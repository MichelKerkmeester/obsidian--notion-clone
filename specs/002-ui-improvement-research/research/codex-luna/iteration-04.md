# Codex-luna UI improvement research — iteration 04

## Focus

Toolbars and view controls: icon-button semantics and state, the view switcher, settings scope, database/view selectors, and add/new affordances. This pass audits the full database view and the embedded renderer, with particular attention to controls that collapse, move, or change meaning on a phone. It deliberately goes beneath the earlier iterations’ broad toolbar hierarchy and generic popover/menu contracts: the new angles here are state fidelity, view identity, touch discoverability, and creation intent.

## Current-UI findings (file:line)

1. The common icon-button factory relies on a visual tooltip but does not establish a reliable control contract. `createIconButton` creates a button with an empty attribute object and calls `setTooltip` (`src/views/ToolbarRenderer.ts:1768-1777`), while refresh is the exception and adds an explicit `aria-label` (`src/views/ToolbarRenderer.ts:292-327`). Filter, sort, group, Properties, Settings, export, and several other controls therefore share one implementation without an explicit accessible name, `type="button"`, or trigger state. The view-config trigger is especially exposed: it has a label passed to the tooltip but no expanded/controls state (`src/views/ToolbarRenderer.ts:1603-1614`). The CSS only gives `.is-active` a hover background (`styles.css:1320-1364`), so an open panel has no durable toolbar state.

2. View tabs look like tabs but are only ordinary buttons. Each tab is created as a `button`, receives an active class, and switches by numeric index; there is no tablist/tab relationship, `aria-selected`, `aria-controls`, keyboard navigation, or explicit button type (`src/views/ToolbarRenderer.ts:625-651`). The add and overflow tab buttons also have no semantic state (`src/views/ToolbarRenderer.ts:654-663`, `src/views/ToolbarRenderer.ts:770-793`). A stable ID-aware resolver already exists in `src/data/ViewSelection.ts:16-43`, but the toolbar callback and `DatabaseView.switchView` still pass the position rather than a stable view identity (`src/views/DatabaseView.ts:1876-1888`, `src/views/DatabaseView.ts:2969-2978`). Reordering or an external refresh can therefore make focus and active-tab continuity fragile.

3. Overflow hides views without telling the user how much was hidden or which view is selected in the overflow surface. The collapse algorithm always preserves the active tab in the visible strip (`src/views/ToolbarRenderer.ts:741-768`), then builds a `⋯` button whose dropdown options contain only hidden views (`src/views/ToolbarRenderer.ts:770-793`). However, it passes the current numeric index as the dropdown value even though that active view is normally absent from those options. The result is a view switcher that can show the active view in one place while its “more” control has no selected option, no hidden-count cue, and no compact “Views” label. On phones the tab strip is clipped inside an overflow-hidden flex item (`styles.css:15366-15375`), making the missing count especially consequential.

4. View management is discoverable only through desktop gestures. Rename and the view menu are wired to `contextmenu` and double-click (`src/views/ToolbarRenderer.ts:642-649`), while tab reordering is explicitly disabled on phones (`src/views/ToolbarRenderer.ts:631-634`). `showViewTabMenu` contains useful actions—rename, duplicate, change type, move, and delete—but is reachable only after the hidden context-menu gesture (`src/views/ToolbarRenderer.ts:796-859`). The existing phone reorder-control pattern uses small sibling buttons elsewhere (`styles.css:1651-1685`, `styles.css:15402-15406`); the view strip has no equivalent explicit action affordance.

5. “Settings” does not reveal whether it changes the database or the current view. The trigger is a single gear-labelled button (`src/views/ToolbarRenderer.ts:1603-1614`), but the panel renders a “Current database” section followed by “Current view” (`src/views/ViewConfigPanelRenderer.ts:248-267`). Full view wiring makes both scopes editable (`src/views/DatabaseView.ts:4589-4639`); embedded wiring makes the database section read-only while still exposing current-view controls (`src/views/EmbeddedDatabaseRenderer.ts:1756-1801`). A user entering Settings cannot know the scope from the toolbar, and the trigger does not reflect whether configuration is open or contains non-default view state.

6. The same floating number badge communicates different kinds of state. Filter and Sort badges count active rules (`src/views/ToolbarRenderer.ts:1575-1601`), whereas the Properties/column button badge counts every visible column (`src/views/ToolbarRenderer.ts:1632-1649`). Because the generic badge renders any positive number as the same accent pill (`src/views/ToolbarRenderer.ts:1801-1804`, `styles.css:1551-1566`), a default table can show a prominent Properties count even when the user has changed nothing. That competes with the genuinely actionable filter/sort counts and makes the number’s noun unclear.

7. The database selector contains nested interactive buttons. A database row is itself a `button` (`src/views/ToolbarRenderer.ts:425-440`), then its up/down reorder controls are appended as child buttons (`src/views/ToolbarRenderer.ts:441-468`). This is invalid interactive nesting and creates ambiguous activation, keyboard focus, and screen-reader output. The grid layout confirms that the row and move controls are intended to occupy separate columns (`styles.css:8430-8445`), and the phone rule preserves the same four-column structure (`styles.css:15520-15522`), so the fix can preserve the visual design while correcting the interaction model.

8. Frontmatter embeds have an “open full view” action in the renderer contract but no visible toolbar escape hatch. `EmbeddedDatabaseRenderer` supplies `openFullView` (`src/views/EmbeddedDatabaseRenderer.ts:1379`) and sets `showDatabaseChrome` plus `hideDatabaseActions` for frontmatter embeds (`src/views/EmbeddedDatabaseRenderer.ts:1390-1394`). In that mode `ToolbarRenderer` renders a passive database heading (`src/views/ToolbarRenderer.ts:156-209`); its full-view button exists only in the compact title-row branch used when `showDatabaseChrome` is false (`src/views/ToolbarRenderer.ts:227-249`). The configuration panel also tells the user that database settings are read-only in an embed (`src/views/EmbeddedDatabaseRenderer.ts:1756-1761`), but does not provide the missing expand control in the same surface.

9. The primary New click can be consumed by overlay cleanup. `DatabaseView` records whether a mousedown occurred with an active overlay (`src/views/DatabaseView.ts:562-565`), and `guardedCreateEntry` closes the overlay and returns when that flag or a current overlay is present (`src/views/DatabaseView.ts:839-865`; the calendar path follows the same rule at `src/views/DatabaseView.ts:867-872`). The toolbar still presents New as the primary action (`src/views/ToolbarRenderer.ts:1716-1739`). A user who deliberately taps New while a filter, settings, or export surface is open may therefore need a second tap, with no feedback that the first tap was intercepted.

10. New can silently mean different things depending on hidden context. The toolbar label changes to “New from template” when a template is configured, but on a phone that label is removed and only the icon remains (`src/views/ToolbarRenderer.ts:1716-1730`). The action disables confirmation and ultimately flows into template loading in `createBlankEntry` (`src/data/TemplateToolbarAction.ts:20-31`, `src/views/DatabaseView.ts:3598-3610`). Calendar and timeline creation likewise inject today’s date when no defaults are supplied (`src/views/DatabaseView.ts:3580-3596`), while the button still says simply “New” (`src/views/ToolbarRenderer.ts:1716-1729`). The control’s icon and tooltip do not expose either the template or date intent at the point of touch.

11. Add view is a flat list of layouts, not a choice of creation intent. The plus button disappears at the 15-view limit (`src/views/ToolbarRenderer.ts:654-663`), and otherwise opens seven undifferentiated view-type rows (`src/views/ToolbarRenderer.ts:921-962`). The implementation seeds a new view from `db.views[0]` (`src/views/DatabaseView.ts:2981-3020`), while “duplicate current view” is a separate context-menu action (`src/views/ToolbarRenderer.ts:816-825`, `src/views/DatabaseView.ts:3473-3493`). This makes it hard to predict whether a new view preserves useful layout settings, and makes the capacity limit disappear rather than explain itself.

## Anytype/AppFlowy patterns

### Anytype

- Anytype’s menu architecture models database controls as distinct view/list, view/settings, view/layout, templates, and new-object entries rather than one opaque gear surface. Its menu documentation explicitly lists those database menu categories and treats menu items as composable affordance slots ([Anytype menu architecture](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/menu/README.md)). The useful lesson for this plugin is semantic grouping: a toolbar trigger can still be compact, but its label and open state should say whether it controls the view, the source, layout, or creation.
- Anytype’s recent focus-and-flow direction treats tabs as first-class workspace controls: tabs can be reordered and pinned, and advanced filters remain available without making every control permanently visible ([Anytype February 2026 update](https://blog.anytype.io/february-community-update-2026/)). That is a stronger model for Note Database’s tab strip than relying on desktop-only context menus: selection, tab management, and overflow should each have a reachable control path.
- Sets can create objects from the current filtered context, with relation filters pre-populated for the new object ([Anytype workflow update](https://blog.anytype.io/workflow-nirvana/)). The transferable pattern is not automatic note mutation; it is visible creation context. A “New” affordance should disclose whether it creates a template-based record, a date-bound event, or a record in the current view before the user commits.

### AppFlowy

- AppFlowy presents a database as one shared data source with multiple named views, then lets the user click the view name and use “Add View” to create another perspective ([AppFlowy databases](https://appflowy-io-appflowy.mintlify.app/core/databases)). Its documentation separates per-view filters, sorts, and field visibility from the shared rows. This supports a clearer Settings scope in the plugin: “View settings” should own the current view’s layout and visible fields, while database-level settings should be explicitly named.
- AppFlowy’s toolbar gives filter and sort their own explicit add flows and lets multiple sorts be reordered, while the field/header surface exposes field actions ([AppFlowy databases](https://appflowy-io-appflowy.mintlify.app/core/databases), [AppFlowy Grid View](https://appflowy-io-appflowy.mintlify.app/core/grid-view)). The useful distinction is between an active-rule count and a structural field count. Note Database should preserve badges for active filters/sorts but express Properties as visibility state, such as “2 hidden,” or omit a badge at the default.
- AppFlowy uses a visible `+ New` action at the bottom of a grid and a `+` affordance in the field header, with keyboard support documented alongside the row action ([AppFlowy Grid View](https://appflowy-io-appflowy.mintlify.app/core/grid-view)). This gives creation a stable, local anchor in addition to the global toolbar. It is a good model for keeping Note Database’s New action single-tap and for offering a view-local creation affordance where a calendar day or grouped context supplies meaningful defaults.

### Notion where useful

- Notion treats database tabs as visible view identity and consolidates layout, properties, filter, sort, and group under “View options” ([Databases reimagined](https://www.notion.com/en-gb/help/guides/databases-reimagined-whats-changed)). The pattern worth adopting is a trigger whose name describes the current scope and whose panel mirrors that scope, not necessarily Notion’s exact visual treatment.
- Notion documents both a top-level New button and view-local `+ New` placements, including a calendar-day affordance; its inline databases also expose an expand-to-full-page control ([Intro to databases](https://www.notion.com/help/intro-to-databases)). These patterns directly address the plugin’s swallowed New tap, calendar date ambiguity, and frontmatter embed escape hatch while remaining display/control changes.

## Open threads for later iterations

- Test the tablist contract with 15 long or translated view names, RTL text, a narrow phone, and an active tab that is moved while the overflow disclosure is open. Decide whether arrow keys activate immediately or move focus before activation.
- Verify focus restoration after switching from the view-actions affordance into Settings, Add view, and the overflow list; this should build on the prior overlay work without re-opening a generic popover audit.
- Measure whether an active-state badge for Properties is more legible than a hidden-count label when the schema has many fields, and test high-contrast themes where the current accent pill is already prominent.
- Exercise frontmatter and codeblock embeds separately: their editability, full-view escape hatch, and New affordance should remain distinct, especially when a template or calendar default is configured.
- Consider a later information-architecture pass for view-type changes: replacing a current view’s layout is a different operation from adding a view, and the current context menu does not preview what per-view settings will be reset (`src/views/ToolbarRenderer.ts:861-900`; `src/views/DatabaseView.ts:2355-2405`).
