# Iteration 5 — Visual design system

## Focus

Color tokens, typography scale, spacing, radius, and dark/light theming across the Note Database plugin. The prior codex-luna iterations established interaction, density, empty-state, menu, and toolbar opportunities; this pass treats the visual primitives underneath those surfaces as a cross-renderer contract. The goal is not a new theme UI. It is to make the existing renderer family read as one product while inheriting Obsidian themes safely.

Research snapshot: 2026-08-27. External references are official Anytype/AppFlowy/Notion sources.

## Current-UI findings (file:line)

- The plugin has a useful starting token block, but it is scoped to `.note-database-container` and mixes geometry, semantic colors, typography, and component defaults in one namespace. The only dark-theme override in that block is current-time lightness (`styles.css:63-134`). The settings host and modal then redeclare only the radius variables (`styles.css:136-156`, `styles.css:2929-2934`). This means a future surface/text token can silently work in the main view but fall back or inherit differently in settings, a modal, or a body-level portal.

- The option palette is repeated in CSS and TypeScript rather than being a single visual contract. Status background/foreground variables are declared once near the root (`styles.css:85-116`), then repeated in number display rules (`styles.css:4371-4387`), display-style swatches (`styles.css:4563-4578`), the color picker (`styles.css:5606-5671`), status badges (`styles.css:5890-5984`), and record-icon styles (`styles.css:15922-16015`). The same hue list also exists in `src/data/RecordIcon.ts:1-12`, `src/data/OptionRegistration.ts:9-12`, and `src/views/ChartRenderer.ts:1576-1594`. Drift is already visible: status red uses a different foreground in the badge rules than the top token declaration (`styles.css:85-116`, `styles.css:5890-5998`).

- One persisted `StatusColor` vocabulary is doing several jobs that have different visual semantics. Number ratings/progress/rings reuse the status palette (`src/views/NumberDisplayRenderer.ts:1-75`, `src/data/types.ts:18-34`); dates turn the same family into urgency (`src/views/CellRenderer.ts:391-407`); conditional formats assign it to every view surface (`src/data/ConditionalFormatting.ts:135-165`); and group labels use the colors as badges (`src/views/GroupLabelRenderer.ts:35-46`). A user-selected red tag and an overdue/error signal can therefore look equivalent even though one is categorization and the other is meaning.

- Conditional formatting is a full background paint, not a theme-aware emphasis layer. The data path sets `--db-conditional-format-bg` and `--db-conditional-format-fg` from the status palette (`src/data/ConditionalFormatting.ts:135-165`), while CSS paints the matched element and, for record rules, all non-matched table cells (`styles.css:469-496`). The foreground variable is not consumed by that base rule. This can overpower hover/selection, produce low contrast in a dark theme, and make board/gallery/list/detail cards visually louder than the table.

- Typography has roles in practice but not in the token model. The base is fixed at `13px` with `1.4` line-height (`styles.css:120-130`); the page title is a fixed `28px`, bold serif (`styles.css:705-750`, `styles.css:900-929`); summaries use separate `11px`/`12px` values (`styles.css:3425-3492`, `styles.css:444-467`); and renderer-specific cards introduce their own `13px`/`14px` title and `12px` metadata metrics (`styles.css:7945-7970`, `styles.css:8116-8223`). This is not just a scale issue: the title’s custom serif fallback stack can diverge from a vault’s chosen interface font and CJK fallback, while smaller labels lack an explicit line-height contract.

- Spacing and radius are similarly fragmented. Only `sm=4px`, `md=6px`, and `lg=8px` are named at the root (`styles.css:63-84`), but controls use pill radius `999px`, icon/control radii `28px`/`7px`/`5px`, popovers and icon pickers use `12px`, and components carry independent gaps and padding (`styles.css:1158-1235`, `styles.css:2936-2992`, `styles.css:3425-3492`, `styles.css:7744-7813`, `styles.css:8082-8223`, `styles.css:15939-15996`). The visual rhythm therefore changes between table, list, gallery, settings, and icon-picker surfaces even when they represent the same fields.

- Elevation is light-biased and globally flattened. Body-hosted popovers, cards, and other surfaces are forced through one black shadow override (`styles.css:16429-16460`), while calendar/timeline interactions add more raw black shadows at multiple strengths (`styles.css:14099-14110`, `styles.css:14203-14218`, `styles.css:14870-14882`, `styles.css:14953-14959`). The dark theme currently changes only current-time lightness (`styles.css:132-134`), so elevation does not adapt with the surrounding theme.

- Charts bypass the plugin container’s visual context. `ChartRenderer` reads CSS variables from `document.body`, not from the database container (`src/views/ChartRenderer.ts:75-93`), falls back to a separate blue/slate palette (`src/views/ChartRenderer.ts:1565-1574`), hardcodes an amber mixed-series line (`src/views/ChartRenderer.ts:800-823`), hardcodes label and donut-center colors/fonts (`src/views/ChartRenderer.ts:1132-1143`, `src/views/ChartRenderer.ts:1230-1242`), and keeps static palette/reference-line values in separate files (`src/data/ChartPalettes.ts:1-22`, `src/views/ChartToolbarRenderer.ts:46-55`). A chart can therefore be readable in the main theme but inconsistent with conditional formatting and dark-mode contrast.

- Focus treatment is only scoped to the main container (`styles.css:187-206`), even though color/icon pickers append their popup to `document.body` (`src/views/OptionColorPicker.ts:15-16`, `src/views/IconPickerPopover.ts:23-27`). Native controls in settings and modal surfaces also inherit host behavior rather than an explicit plugin `color-scheme` contract (`styles.css:136-156`, `styles.css:2936-2992`). This leaves a visual-system gap at exactly the surfaces where theme switching and keyboard focus are most noticeable.

## Anytype/AppFlowy patterns

Anytype’s source makes the semantic/decorative distinction explicit. Its base variables separate text roles, shape/background roles, system accent/destructive roles, color families, tag colors, icon colors, and typography tokens in one vocabulary ([Anytype base token variables](https://raw.githubusercontent.com/anyproto/anytype-ts/develop/src/scss/_vars.scss)). Its dark theme overrides those semantic roles as a set and declares `color-scheme: dark`, including separate dark surface/text values and a dark elevation recipe rather than merely swapping one accent ([Anytype dark-theme variables](https://raw.githubusercontent.com/anyproto/anytype-ts/develop/src/scss/theme/dark/common.scss)). The pattern worth adopting is token provenance: a component asks for `text-secondary` or `tag-blue`, not a raw blue that is later reused as an error or chart line. That makes a theme change a controlled mapping exercise.

AppFlowy’s Flutter UI consumes a central theme object for spacing, radii, fills, text colors, and text styles. In its settings menu, padding, border radius, hover/selected fills, primary text, and body text style all come from `AppFlowyTheme` rather than local constants ([AppFlowy settings theme usage](https://github.com/AppFlowy-IO/AppFlowy/blob/main/frontend/appflowy_flutter/lib/workspace/presentation/settings/widgets/settings_menu_element.dart)). Its customization model exposes light/dark/system modes, immediate theme application, custom colors, custom theme JSON, document padding, and font-size scaling ([AppFlowy customization](https://appflowy-io-appflowy.mintlify.app/advanced/customization)). The useful pattern is a small, named set of primitives that every renderer consumes, with user/theme scaling applied at the primitive layer.

AppFlowy also makes row height a view-level presentation choice—compact, medium, or tall—alongside properties, grouping, and calculations ([AppFlowy Grid View settings](https://appflowy-io-appflowy.mintlify.app/core/grid-view)). For this plugin, the transferable part is not adding another settings surface now; it is keeping row/card rhythm expressible through shared tokens so a later density decision does not require rewriting each renderer.

Notion’s database model reinforces the separation between data and presentation: each view owns layout, property visibility, filters, sorts, groups, and subgroups ([Notion views, filters, and sorts](https://www.notion.com/help/views-filters-and-sorts)). Applied here, visual tokens should remain global and stable while a view chooses presentation details such as a shared density or emphasis mode. That avoids encoding theme or visual semantics into note-body values.

## Open threads for later iterations

- Validate the alias map against popular Obsidian light, dark, high-contrast, and accent-heavy themes, including live theme switching and system theme changes. Add contrast checks for text, borders, focus, status pairs, charts, and color-blind distinguishability.
- Decide whether the serif title should remain the default product signature after testing vault font preferences, CJK fallback, RTL text, zoom, and narrow widths. Avoid changing the title identity without evidence from the next visual review.
- Test the spacing/radius primitives at 320px, 375px, tablet, and desktop widths across table, board, gallery, list, calendar, timeline, settings, and body-hosted pickers. Verify that no sticky offset or scroll behavior changes accidentally.
- Stress-test the conditional-format precedence matrix against hover, selection, editing, drag/move, and empty values across every renderer; specifically verify that record-level tint no longer hides field-level meaning.
- Define chart palette rules for more than eight series, print/export, transparent backgrounds, and user-defined palettes, then decide whether palette choices should be view-scoped or database-scoped without changing note-body data.
