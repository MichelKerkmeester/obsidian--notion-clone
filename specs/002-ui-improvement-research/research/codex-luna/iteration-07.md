# Iteration 07 — AppFlowy UI/UX patterns worth adopting

## Focus

AppFlowy patterns for grid, board, calendar, typed field editors, theming, and row detail. This pass intentionally goes beneath the already-covered recommendations for generic empty states, toolbar layering, overlay/accessibility primitives, semantic theme tokens, object identity, and broad inspector structure. The new seams are:

- a board lane currently communicates a field value while the card repeats that same field;
- moving a card across lanes is a hidden data mutation, not only a reorder;
- scheduled calendar overflow is a hover affordance rather than a keyboard-safe list transition;
- calendar field selection does not explain the resulting all-day/timed event model;
- field actions are reachable from row surfaces without making view scope versus schema scope clear;
- draft option editing and type conversion lack stable, inspectable intermediate states;
- row detail treats view visibility as if it were the record’s field inventory.

All proposals remain display-only or improve the presentation of existing explicit actions. No recommendation requires writing to a note body.

## Current-UI findings (file:line)

1. **Board cards repeat the active grouping field.** The card field loop renders every column other than the title at `src/views/BoardRenderer.ts:611-656`, while the group and subgroup headers already render their labels, counts, and summaries at `src/views/BoardRenderer.ts:311-345` and `src/views/BoardRenderer.ts:377-410`. The result is a “Status: In progress” line repeated in the card underneath an “In progress” lane. The two-level metadata treatment is visible in `styles.css:7405-7484`. This is wasted vertical space on phones and weakens the visual meaning of a lane.

2. **Board movement has two meanings but one visual language.** `src/views/BoardRenderer.ts:524-575` shows a drag target and commits the drop; `src/views/BoardRenderer.ts:866-894` updates group and subgroup field values when the destination differs; and the mobile move menu at `src/views/BoardRenderer.ts:739-799` only labels destinations. The pure drop model distinguishes “move” from “reorder” at `src/data/BoardContainerDrop.ts:82-94`, but the UI does not announce that crossing a lane changes a property. The current drop feedback is primarily a shadow/background state in `styles.css:7303-7315`.

3. **Scheduled calendar overflow is not a real control.** Month overflow is a `div` with `+N` text and mouse hover/click handlers at `src/views/CalendarRenderer.ts:255-300`; all-day overflow repeats the pattern at `src/views/CalendarRenderer.ts:600-632`. The CSS supplies typography and a pointer cursor but no focus treatment at `styles.css:13236-13246` and `styles.css:13828-13844`. This is distinct from the previously identified undated/unscheduled-row problem: these are valid dated events hidden by a lane limit, with no keyboard path to the remaining events.

4. **Calendar setup has field selectors but no event-role preview.** The data controls select start, end, title, and scale at `src/views/CalendarToolbarRenderer.ts:127-176`; appearance controls select color and record icon at `src/views/CalendarToolbarRenderer.ts:251-293`. The user must infer the result from render code: month cards show title/date/icon at `src/views/CalendarRenderer.ts:205-242`, while timed events show title/time at `src/views/CalendarRenderer.ts:733-771`. The model supports date-only versus timed values and status-derived colors at `src/data/CalendarTimelineModel.ts:764-837`, but that distinction is not surfaced while configuring the view.

5. **A card-field context menu can look like a cell editor but expose schema actions.** Board fields attach the column menu to both the value and label at `src/views/BoardRenderer.ts:645-654` and `src/views/BoardRenderer.ts:1123-1126`; the detail panel does the same at `src/views/RecordDetailPanel.ts:248-256`. The menu includes edit-property, hide, move, change-type, and delete actions at `src/views/ColumnMenu.ts:68-95` and `src/views/ColumnMenu.ts:158-250`. The interaction is powerful, but a mobile user cannot tell whether “hide” means this view or every database view, or whether a menu opened from a card is about this value or the shared field definition.

6. **Status-option drafts are rebuilt as a whole list.** The option list is cleared and reconstructed by `src/views/modals/StatusOptionsModal.ts:189-281`; a color change triggers another list render at `src/views/modals/StatusOptionsModal.ts:247-260`. A text edit updates a live badge preview at `src/views/modals/StatusOptionsModal.ts:225-245`, but the editor has no keyed-row contract for preserving focus, caret position, or the active row while another option changes. AppFlowy-like add, edit, reorder, and delete workflows need a less fragile draft surface.

7. **The option editor previews one badge, not the real themed surfaces.** The current preview is a status badge at `src/views/modals/StatusOptionsModal.ts:225-260`; the same status value is rendered in board fields at `src/views/BoardRenderer.ts:1023-1033` and drives calendar event color at `src/data/CalendarTimelineModel.ts:825-837`. Board cards and calendar events use different surfaces and emphasis rules in `styles.css:5890-5998` and `styles.css:13615-13643`. A color that looks fine as a badge may be muddy on a secondary board lane or unreadable as a calendar event tint.

8. **Type-conflict resolution offers a target type, not a conversion preview.** The conflict modal collects writers, current types, target type, and validation at `src/views/modals/PropertyTypeConflictModal.ts:83-125` and `src/views/modals/PropertyTypeConflictModal.ts:137-279`; the underlying conflict description is assembled at `src/data/PropertyTypeConflict.ts:137-180`. There is no representative-value preview showing what a date, select, number, or relation cell will render as, nor a visible unresolved count before the explicit resolution action.

9. **Row detail receives the current view’s visible columns instead of the record’s full schema.** `src/views/DatabaseView.ts:10606-10621` passes `getVisibleColumns(...)` into `RecordDetailPanel`; the panel then renders only that `columns` array and hides empty values at `src/views/RecordDetailPanel.ts:186-195`. Table peek has a separate visible-versus-hidden split at `src/views/TableRecordPeek.ts:138-180`, so the behavior differs by entry point. The panel geometry already anticipates a scrollable, constrained surface at `styles.css:7569-7644`.

10. **Detail refresh replaces the panel DOM.** `src/views/RecordDetailPanel.ts:95-101` calls `renderContent`, which empties and rebuilds the panel at `src/views/RecordDetailPanel.ts:152-219`; database refresh synchronization is driven from `src/views/DatabaseView.ts:10631-10678`. That can discard scroll position, an open field editor, and any future disclosure state during metadata or view refresh. This is a refresh-stability issue, separate from the prior iteration’s question of how to open and navigate an inspector.

## Anytype/AppFlowy patterns

### AppFlowy

- **One dataset, multiple projections.** AppFlowy describes rows, fields, and views as one database: Grid, Board, and Calendar are different views of the same rows, and field edits propagate across them. Its [database model and field operations](https://appflowy-io-appflowy.mintlify.app/core/databases) make the field definition explicit, including rename, hide, reorder, duplicate, and type-specific configuration. Adopt the distinction between a view presentation action and a shared field-definition action; it makes the current menu ambiguity concrete.

- **Board lanes carry a typed property meaning.** AppFlowy Board groups by select or checkbox, creates columns from those options, and moving a row between columns changes the grouping value. That is a useful mental model for Note Database, but it requires a visible “this changes the field” cue so drag does not masquerade as simple ordering. AppFlowy’s [Board behavior](https://appflowy-io-appflowy.mintlify.app/core/databases) also supports compactness and group visibility, which reinforces omitting a redundant grouping field from cards.

- **Typed cells have an editor contract.** AppFlowy’s [Grid view](https://appflowy-io-appflowy.mintlify.app/core/grid-view) gives each field a type icon and field-header actions, uses type-appropriate click or keyboard entry, and opens a row detail with all fields plus a document area. The valuable pattern is not a particular popup: it is a stable distinction between display, edit, and field-definition states, plus a predictable “row detail is authoritative” fallback.

- **Calendar configuration explains the data model.** AppFlowy’s [Calendar view](https://appflowy-io-appflowy.mintlify.app/core/calendar-view) separates date-only all-day events from date-and-time events, supports month/week/day scales, lets users choose event-card fields and compactness, and opens a clicked event in row detail. This makes the selected date field’s consequences legible before the user scans the calendar.

- **Customization is surface-aware.** AppFlowy exposes view-specific hidden columns, widths, row height, and compact mode through [customization settings](https://appflowy-io-appflowy.mintlify.app/advanced/customization). The pattern worth borrowing is a preview of density and field visibility in the surface being changed, rather than a generic setting whose effects must be discovered elsewhere.

### Anytype

- **Typed cells are shared presentation primitives.** Anytype’s [cell component documentation](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/cell/README.md) and [widget documentation](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/widget/README.md) frame cells and collection widgets as typed views over objects. For this plugin, that suggests a shared field-role descriptor used by grid, board, calendar, and row detail: the same field should declare its display label, editability, color semantics, and whether it is a view grouping field.

- **Object presentation should not erase object inventory.** Anytype’s object-oriented UI keeps the object and its properties distinct from the particular widget or collection view. Applied here, a hidden column is a presentation choice, not proof that the record has no such field. This is the specific Anytype lesson behind showing “not shown in this view” in row detail, without reopening the broader object-identity work from iteration 6.

- **Theme work is strongest when validated in context.** Anytype’s [theme variables](https://github.com/anyproto/anytype-ts/blob/develop/src/scss/_vars.scss) and [dark-theme roles](https://github.com/anyproto/anytype-ts/blob/develop/src/scss/theme/dark/common.scss) organize color by semantic use. The new angle here is operational: option editing should show the actual board-card and calendar-event surfaces in the active theme, not merely expose another palette abstraction.

### Notion where useful

- Notion treats each database item as a page and supports table, board, and calendar views with peek/full-page detail in its [database introduction](https://www.notion.com/help/intro-to-databases). Its [customizable layouts](https://www.notion.com/en-gb/help/layouts?nxtPslug=layouts) separate pinned/main properties from a details panel and let hidden property groups remain searchable. That is a strong precedent for a row-detail field inventory independent of the current view’s visible columns.

## Open threads for later iterations

- Test the board cue with manual order, active sort, nested subgroup, read-only mode, and a narrow touch viewport; confirm that “move” never silently appears to be “reorder.”
- Decide whether the calendar overflow destination should remain a popover or become a bottom sheet on phones; preserve the same event-list semantics and focus return either way.
- Prototype the calendar role preview and status theme matrix with long labels, missing colors, custom Obsidian themes, and high-contrast settings.
- Measure large schemas before showing all fields in row detail; the next iteration should settle virtualization, search, and whether hidden fields should be lazily rendered.
- Verify keyed detail refresh during frontmatter changes, file renames, filtering, and inline editing; no stale field value should survive a row identity change.
- Reconcile type-conversion previews with the existing conflict model and keep conversion logic out of the view layer.
