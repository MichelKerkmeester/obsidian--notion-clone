# Codex-luna UI/UX research — iteration 01

## Focus

Iteration 1 of 10 for the codex-luna track: overall UI/UX audit, with emphasis on visual hierarchy, cross-view consistency, information density, and first-run or empty states.

The audit follows the real dashboard and embedded render paths in `src/views/`, the source/query boundaries in `src/data/`, and the shared presentation rules in `styles.css`. The prior-artifact directory was empty at audit time, so there were no earlier codex-luna findings to repeat. All recommendations preserve the research constraints: mobile-safe rendering, iCloud-safe display-only behavior with no note-body writes, MIT-forkability, and rebase-clean changes.

## Current-UI findings (file:line)

1. **The UI has several meaningful data states, but most of them collapse into an indistinguishable empty surface.** The dashboard separately detects no database, no columns, and a source-read failure at `src/views/DatabaseView.ts:6353-6381`, but after records enter the pipeline, only the final `this.rows` result is passed to the view dispatch at `src/views/DatabaseView.ts:6406-6435`. `src/data/RowPipeline.ts:23-111` applies sort, search, status, filters, and result-limit in sequence without returning stage counts. A zero result therefore cannot tell the user whether the folder is empty, a filter/search excluded everything, a limit is active, or the selected view cannot place the records. `src/data/DataSource.ts:226-287` makes the source boundary meaningful by excluding view-definition files and applying folder/rule-tree matching, but that distinction never reaches the UI.

2. **First-run setup is technically detected but not designed as a guided state.** A database with no schema columns gets a plain `.db-empty` string at `src/views/DatabaseView.ts:6366-6371`; the embedded path does the same for missing columns or read failures at `src/views/EmbeddedDatabaseRenderer.ts:923-960`. The dashboard’s no-database state is only a title plus one create button at `src/views/DatabaseView.ts:6624-6634`. Meanwhile, the toolbar infers `needsSetup` and marks the toolbar read-only when there are fewer than two columns at `src/views/DatabaseView.ts:1868-1956`, but does not expose the next setup decision. The result is a state that explains what is missing neither in context nor in terms of the next safe action.

3. **Zero-result behavior varies by renderer, so switching views changes the meaning of “empty.”** Ungrouped tables still render a header, table shell, and new-row affordance when `rows` is empty at `src/views/TableRenderer.ts:69-86`; grouped tables instead replace the content with generic `common.noMatchingData` at `src/views/TableRenderer.ts:88-104`. Board rendering always creates the board and iterates groups at `src/views/BoardRenderer.ts:116-143`; an empty column gets a count of `0` and a blank card area with a create control at `src/views/BoardRenderer.ts:340-374`. Gallery and list both show `Total 0` followed by an otherwise blank surface at `src/views/GalleryRenderer.ts:90-99` and `src/views/ListRenderer.ts:85-92`. This inconsistency is a hierarchy problem, not just missing copy: some views foreground an action, some foreground a count, and some show no recovery path.

4. **The plugin already proves that reason-aware empty states work, but only charts use the pattern.** `src/views/ChartRenderer.ts:96-110` distinguishes missing fields, missing selection, no records, hidden groups, and invalid axis ranges. `src/views/ChartRenderer.ts:555-608` pairs several reasons with a targeted recovery action such as choosing a default field, showing groups, or resetting the axis. The table, board, gallery, list, calendar, and timeline paths do not share this level of semantic feedback; calendar’s helper is a single generic `.db-empty` at `src/views/CalendarRenderer.ts:2216-2218`.

5. **Empty groups are intentionally synthesized, but their visual treatment makes them look like broken or unfinished content.** `src/data/GroupVisibility.ts:17-59` defaults empty status/select groups into the group list and can inject missing options with count `0`. DatabaseView passes these groups to table, board, gallery, and list renderers at `src/views/DatabaseView.ts:9700-9751`. Board shows the zero count and an empty drop area at `src/views/BoardRenderer.ts:311-374`; gallery and list create a section but no explicit “empty group” message at `src/views/GalleryRenderer.ts:101-137` and `src/views/ListRenderer.ts:94-128`. Users cannot tell whether an empty column is a valid destination, hidden data, or a configuration artifact.

6. **Calendar and timeline can silently omit records that are valid in the source view.** Calendar only shows an empty explanation when no date field is configured at `src/views/CalendarRenderer.ts:118-123`; timeline exits when there is no start field or no event model at `src/views/CalendarTimelineRenderer.ts:230-248`. The dashboard passes the same filtered row set into those renderers at `src/views/DatabaseView.ts:6422-6425`, but there is no visible unscheduled/undated count or companion list for records lacking the selected date. This is a partial-view empty state that can be mistaken for successful filtering.

7. **The header has a strong identity layer, but its action hierarchy is flat and expensive on narrow screens.** Toolbar rendering places database identity, optional description, view tabs, search, width, filters, sorts, view configuration, grouping, columns, sync, refresh, export, and creation into adjacent regions at `src/views/ToolbarRenderer.ts:152-285`. Tabs do collapse when space runs out through the observer at `src/views/ToolbarRenderer.ts:625-683`, but the action set remains broad. On phones, the toolbar becomes a vertical stack and the right action rail becomes horizontally scrollable at `styles.css:15287-15391`; the fixed-width search control alone consumes up to `42vw` at `styles.css:15372-15383`. This preserves reachability but weakens the visual answer to “what should I do first?”

8. **Information density is tuned per view rather than by a shared content hierarchy.** Table cells are fixed at 34px with 13px type at `styles.css:4049-4077`; gallery cards use a fixed 250px grid rhythm at `styles.css:7744-7751`, sticky group headers at `styles.css:7765-7798`, and multi-line metadata rules at `styles.css:7908-8050`; list rows use a wide content-sized grid and a 44px minimum row at `styles.css:8082-8176`. Gallery and list also hide empty fields by default in their renderer-specific field loops at `src/views/GalleryRenderer.ts:163-257` and `src/views/ListRenderer.ts:153-251`. These are reasonable individual choices, but there is no shared “essential versus detailed” density contract, so the same record changes emphasis dramatically when the user switches layout.

9. **Failure presentation leaks implementation detail and can erase the surrounding hierarchy.** A render exception is written as a generic empty block containing the error, current database information, and part of the stack at `src/views/DatabaseView.ts:1238-1251`; the CSS intentionally presents it as a monospace pre-wrap block at `styles.css:6154-6158`. Data-source failures use generic inline strings at `src/views/DatabaseView.ts:6373-6381` and `src/views/EmbeddedDatabaseRenderer.ts:950-957`. There is no consistent separation between a user-recoverable read problem, a setup problem, and an actual plugin defect, nor a small retry/details hierarchy. Refresh also removes current result roots before rendering again at `src/views/DatabaseView.ts:10631-10646`, while the toolbar exposes only a refresh icon/badge at `src/views/ToolbarRenderer.ts:288-329`; a slow refresh can therefore look like a blank state.

## Anytype/AppFlowy patterns

- **Notion: identity, views, and configuration are separate layers.** Notion keeps the same database source behind multiple named tabs, lets each view own its layout, property visibility, filters, sorts, and grouping, and puts the configuration in one `View settings` or `View options` surface. It also supports hiding empty groups and offers side-peek opening for keeping the database context visible. The relevant patterns are documented in [Notion’s views, filters, sorts and groups guide](https://www.notion.com/help/views-filters-and-sorts) and the [databases reimagined guide](https://www.notion.com/en-gb/help/guides/databases-reimagined-whats-changed). The benefit here is a predictable scan order: identify the source, choose the view, then adjust the view, with secondary actions not competing with the result surface.

- **Notion: quick filters are explicitly different from durable view structure.** Notion’s quick-filter guidance keeps fast, local narrowing close at hand while advanced filter groups remain available but out of the default path. That separation is a useful model for this plugin’s transient search and persisted view filters: the UI should say which state is active and offer a one-step clear path instead of rendering the same blank result for both. This is especially relevant because `ViewStateStore` already treats search as transient while persisted filters/sorts live in view state at `src/views/ViewStateStore.ts:17-119`.

- **AppFlowy: multiple layouts share one database model.** AppFlowy documents Grid, Board, and Calendar as multiple views over the same database structures, with rows, fields, and type options shared across the layouts. See [AppFlowy’s database-view architecture](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/frontend/database-view). The transferable pattern is not a visual clone; it is a shared result contract. Counts, missing-data states, property labels, and empty-state semantics can be computed once and rendered appropriately by each layout, avoiding the current table-versus-board-versus-gallery drift.

- **AppFlowy: partial calendar membership is surfaced instead of discarded.** Its calendar documentation says an event needs a date and that events with an empty date are shown in a separate list of other events; the calendar-view project further describes an unscheduled-events menu/list. See [AppFlowy Calendar](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/frontend/database-view/calendar) and [Calendar View for AppFlowy Database](https://docs.appflowy.io/docs/appflowy/community/appflowy-mentorship-program/mentorship-2022/mentee-projects/calendar-view-for-appflowy-database). This is better than a silent omission because it preserves user trust: the calendar can remain date-focused while still accounting for every source record.

- **AppFlowy: empty and unassigned board states remain meaningful destinations.** Its Kanban documentation describes a non-removable “No Status” group for missing grouping data and explicit creation/drop behavior per group. See [AppFlowy Kanban Board](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/frontend/database-view/kanban-board). Applied conservatively here, a zero group should be visibly intentional and explain what it represents; this does not require changing the plugin’s existing mutation behavior.

- **Anytype: consistent object identity plus progressive property visibility.** Anytype’s current desktop release notes describe type-level icons, header/sidebar/hidden property sections, templates, type widgets, full-page settings with a left sidebar, pinning for faster navigation, and creating objects directly within collections. See [Anytype Desktop 0.46 release notes](https://releases.any.org/desktop-0460). Its public API also treats an object list as an at-a-glance surface with pagination, filtering, name, icon, type, snippet, layout, and details in [List objects](https://developers.anytype.io/docs/reference/2025-11-08/list-objects/). The useful lesson is to establish a stable identity and essential metadata first, then progressively reveal detail; that supports both first-run guidance and density controls without making every card equally noisy.
