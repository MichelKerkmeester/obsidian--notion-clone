# Codex-luna UI/UX research — iteration 06

## Focus

Anytype UI/UX patterns worth adopting for an object-oriented Obsidian database: object identity, a two-sided sidebar model, block-aware record inspection, and the distinction between a live Set/collection and the views used to present it. AppFlowy is the closest comparison for a row that opens into a document, while Notion is useful where its database item/page model exposes a practical interaction pattern.

This pass deliberately goes below the already-covered toolbar, grid, popover, empty-state, responsive, and visual-token work. The design constraint is to make an Obsidian file feel like a coherent object in context without changing the file's Markdown or frontmatter.

## Current-UI findings (file:line)

- Object identity is inconsistent across surfaces. The table peek titles every row with `currentRow.file.basename` and labels its dialog with the basename (`src/views/TableRecordPeek.ts:129-136`), while the full detail panel already resolves the configured title field through `resolveTitleFieldDisplay` (`src/views/RecordDetailPanel.ts:152-185`). The shared resolver supports file name, basename, path, and configured properties (`src/data/TitleFieldDisplay.ts:14-58`), but the table peek does not use it. This is an object-model seam, not only a typography issue: the same file can appear to be different objects depending on where it is opened.

- Both existing inspectors are property-first, not content-aware. The peek renders visible and hidden properties (`src/views/TableRecordPeek.ts:138-180`), and the detail panel loops through fields while skipping the title and hidden empty fields (`src/views/RecordDetailPanel.ts:186-195`). Neither exposes a note outline, embeds, or a body/content region. The underlying row already carries `CachedMetadata` (`src/data/types.ts:116-122`), and the file-field layer already resolves links, embeds, backlinks, and file metadata (`src/data/FileFields.ts:7-21,93-119`), so a read-only contents layer can be derived without inventing a new storage model.

- The two inspection modes have different lifecycles and neither supports a persistent object context. A table peek is a right-docked panel that closes on outside click, Escape, container scroll, and window resize (`src/views/TableRecordPeek.ts:65-127,182-195`); the detail panel is an anchored popover whose cleanup and positioning are local to that panel (`src/views/RecordDetailPanel.ts:104-220`). There is no keep-open/pin affordance, previous/next navigation through the current result set, or explicit “open the whole note” transition that preserves the current object context.

- Relation values lose object provenance in the UI. The schema knows the target database ID (`src/data/types.ts:36-39`), but relation chips are rendered as generic `file-text` links with only a display label (`src/views/RelationValueRenderer.ts:14-35`). An inbound relation index already exists and is metadata-cache based (`src/data/RelationInverse.ts:39-86`), yet `DatabaseView` builds that cache as part of the rollup path and clears the relation caches when rollups are not needed (`src/views/DatabaseView.ts:3410-3447`). This makes “what points to this object?” an available data concept but not a stable object-inspector concept.

- Collection membership and view presentation are merged internally but not explained to the user. Database-level and view-level source rules are combined by `getEffectiveConfig` (`src/views/DatabaseView.ts:4115-4128`); the underlying config separately stores database identity/source rules and view identity/source rules (`src/data/types.ts:263-332`). The visible header exposes database name, icon, and description (`src/views/ToolbarRenderer.ts:152-224`) plus view tabs (`src/views/ToolbarRenderer.ts:251-285`), but no breadcrumb or cue that the active view may narrow the collection.

- The database switcher is a transient list, not workspace navigation. It renders a one-shot “Database list” popover with rows and a current check (`src/views/ToolbarRenderer.ts:369-475`). That is adequate for switching, but it gives no persistent collection/library context, no relationship between a database and its views, and no place for an object inspector to establish “where this object came from.” The existing responsive selector rules (`styles.css:8425-8480,15287-15338,15520-15522`) provide a safe mobile fallback if a desktop rail is introduced.

- The table peek also downgrades typed values to strings. Its `renderProperty` path calls `stringifyValue` (`src/views/TableRecordPeek.ts:215-224`), whereas the detail panel has dedicated field/value rendering for richer values and relations (`src/views/RecordDetailPanel.ts:222-270,313-325`). An object-oriented inspector should share the richer value presenters rather than create a third representation of the same property.

- Record icons are already a database/view-level identity affordance, but they are not paired with a complete object header everywhere. The row icon renderer honors `config.showRecordIcon` and resolves a configured record-icon field (`src/views/DatabaseView.ts:4716-4737`), while the table peek header currently has only the basename title (`src/views/TableRecordPeek.ts:129-145`). A consistent identity header can reuse the existing icon and title plumbing instead of adding another icon setting.

## Anytype/AppFlowy patterns

- Anytype makes the object the stable unit of the interface: an object has an identity, icon, properties, and body content, while relations connect objects and Sets collect many objects into a shared working view. This is the useful mental model for this plugin: a note/file remains the object, the database is a collection query, and a table/board/calendar is a projection. See [Anytype's object metaphor](https://blog.anytype.io/a-new-metaphor/) and its [object API guide](https://developers.anytype.io/docs/guides/get-started/objects/). Adopt the separation of identity, relationships, and presentation; do not copy Anytype's storage or sync model.

- Anytype's sidebar architecture separates workspace navigation from contextual inspection. Its source documentation describes a collapsible left sidebar for vault/library/type/object navigation and a context-sensitive right sidebar for object relations and table of contents ([sidebar component README](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/sidebar/README.md)). For this plugin, that suggests a desktop-only optional collection rail on the left and a unified object inspector on the right, with both collapsing to existing popovers/sheets on a phone.

- Anytype treats content as blocks and routes block types through a common renderer; the documented block system includes databases, covers, featured/relation blocks, and table-of-contents blocks ([block component README](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/block/README.md)). The transferable pattern is not “turn Markdown into Anytype blocks,” but “give an object inspector a content/outline region alongside properties.” Obsidian's cached heading metadata is a safe first increment; it provides a TOC-like bridge without eagerly reading or rewriting note bodies.

- Anytype Sets make collection membership and view choice legible: a Set gathers objects with shared relations, then the user selects how to sort, filter, and view them ([Anytype's Sets explanation](https://blog.anytype.io/a-new-metaphor/)). This maps directly to the plugin's database-level source rules versus view-level source rules. A compact collection/view breadcrumb would communicate that changing a view is not changing the object or the collection itself.

- AppFlowy makes the row detail page a first-class continuation of a database row: properties stay in a property panel, while a document area below supports block content, cover/banner presentation, and row actions. Its docs also state that multiple views share the same underlying database data ([AppFlowy database docs](https://appflowy-io-appflowy.mintlify.app/core/databases)). The pattern worth adopting is a predictable “row identity → properties → document/contents” sequence, with the current table remaining a view rather than the only place a row can be understood.

- Notion provides the pragmatic interaction precedent: every database item is a page, opening in a peek keeps the database context, properties appear at the top, and the page body remains available for blocks ([Notion database introduction](https://www.notion.com/help/intro-to-databases)). Its layouts documentation adds pinned properties, property groups, a details panel, and a main-page area ([Notion layouts](https://www.notion.com/help/layouts)). These patterns support grouping and inspection improvements here, but the implementation should remain display-only because this plugin's source of truth is the user's note.

## Open threads for later iterations

- Decide whether a future explicit “Preview content” action should read the Markdown body, or whether headings, embeds, and links are the right permanent boundary for an iCloud-friendly inspector.
- Define the collection/view vocabulary for databases whose view source rules materially change membership; test the breadcrumb against nested databases and embedded views before adding richer provenance.
- Test pinned inspector navigation against filtered, grouped, and virtualized result sets, including a file rename or metadata-cache refresh while the inspector is open.
- Measure the cost and refresh strategy of a general inbound relation index when rollups are disabled; set caps and cycle handling before exposing graph-like navigation.
- Resolve whether `isType` source rules are stable enough to become a visible object-type badge, rather than implying a type system that the current frontmatter model does not guarantee.
- Validate the left rail/right inspector combination at 320px, 375px, tablet widths, and with an embedded database so navigation never consumes the record canvas.
