# Final Plan: Derived Inverse (Safe Two-Way) Relations
> Reviewed & optimized build plan, from a fresh Grok 4.6 (xhigh-fast) review of this phase's rewritten spec/plan/tasks/checklist plus its synthesis and research.

## Review — strengths, gaps, risks

**Solid.** Do not port Notion `dual_property`. One stored many-to-one wikilink, inbound set computed, `SYNC_WRITES_DEFAULT = false`, no ON path (`research/synthesis.md` verdict + ranked item 10). The scan to invert is real and already in the fork: relation columns by `type === "relation" && relationConfig?.targetDatabaseId` (`RelationRollup.ts:28-32`), `parseRelationValues` (`RelationLinks.ts:23-26`), `getFirstLinkpathDest` (`RelationRollup.ts:71`), `seenPaths` (`69-75`), membership via `recordsByPath` (`50-56,73-74`). `buildRelationRollups` early-returns when the viewed DB has no rollup columns (`:36`) — inverse must be its own entry, not a callee. Rollup cells are already display-only (`types.ts:69`; `CellRenderer.ts:239-241`, `460-465`). Write path is per-path (`DataSource.ts:89,99-120`; `mutateFrontmatter` `288-296`). Empty/dangling/cross-db/self-relation fail-closed behavior can be inherited, not reimplemented.

**Wrong dependency.** Plan DoR and T001 wait on packet `001-live-reports-rollups`. That packet is **vault YAML only** — “no new `src/` module, no fork TypeScript” (`001-live-reports-rollups/spec.md` Purpose). The scan already exists. 001’s product move is to **store Reports-side relation columns** because the fork only rolls up *forward* (`RelationRollup.ts:70-78`). 008 exists to make those stored back-columns unnecessary. Blocking 008 on 001 completion is inverted. Code dependency: **none**. Data dependency for *manual* proof: at least one Expense `Month` wikilink. Unit tests fixture their own edges.

**Wrong call-site budget (correctness trap).** SC-005 / T006 lock hunks to `RelationRollup.ts` + `RelationLinks.ts` and claim refresh scoping is “no new plumbing” (T009) via `EmbeddedDatabaseRenderer.ts:3210-3221` and `planRelationTargetChange.ts:23-49`. That is false for the finance shape:

- `handleDataChangeBatch` refreshes when `relationTargetPaths.has(change.path)` **or** the record matches `relationTargetDatabases` (`DatabaseView.ts:2120-2128`).
- Those sets are filled from **local relation columns on the viewed DB** (`3362-3372`; duplicate at `EmbeddedDatabaseRenderer.ts:3210-3221`): `targetIds` = `columns.filter(type === "relation")`.
- A Report that only has rollup columns (the 008 default surface) has **zero** local relations. `relationTargetPaths` / `relationTargetDatabases` stay empty. Editing or creating an Expense does not refresh the Report view. Stale inbound counts are the silent failure mode — the same class as 001’s “silent empty SUM”.

`planRelationTargetChange` only walks rollups on the *source* DB whose `relationField` matches a changed *local* relation (`23-49`). It does not invalidate a Report rollup when Expenses.Month’s target set changes. T009 as written will not ship SC-002 in a live view.

**Orphan tasks under rollup-only SC-002.** Operator default is rollup-only (open question 1); `RecordDetailPanel.ts:320-323` is deferred (T019). Rollup `list`/`count` render through `row.computed[col.key]` as ordinary rollup cells (`CellRenderer.ts:115-116,656`), **not** `renderRelationValue` chips (`RelationValueRenderer.ts:7-37`). T006 (inverse chip helper in `RelationLinks.ts`) and T008 (first-N chip window) have **no consumer** this phase. Shipping them is dead code in the 2-hunk budget while the refresh hunk is missing.

**EuroFormat analogy is over-claimed.** `EuroFormat.ts:1-10` has zero imports. `RelationInverse.ts` must import `App`, `parseRelationValues`, `ColumnDef`/`DatabaseConfig`, `NoteRecord` (`research/research.md` F7.2). Isolate the *file* and keep call sites small; do not pretend zero imports.

**`enqueueWrite` is private** (`DataSource.ts:99`). T015 cannot spy it without a production export. Spy `processFrontMatter` / `vault.create` paths, or assert the Report file mtime/content is unchanged after an Expense relation click.

**Ambiguous inverse key.** Hunk 1 resolves a missing *local* `relationField` as “a relation column on another DB whose `targetDatabaseId === sourceDatabase.id`”. The full fan-in index unions *all* inbound edges. A Report rollup with `relationField: "Month"` must match columns **named `Month`** that target Reports (Expenses + any other DB that reused that key). `Sales.Report` (different key) is a second rollup column, not magically included. Synthesis Scenario 6 vs hunk 1 must be stated as **key-scoped union**, not “all inbound regardless of column key”.

**Effort.** ~8h M is plausible if chips/UI stay deferred and refresh is in scope. It is not plausible if T006+T008+T013 harness+T019 waiver all land in the same diff. `RelationRollupConfigModal.ts` will not offer a foreign `Month` key; v1 is YAML `rollupConfig.relationField: "Month"` on the Report (same YAML-first posture as 007).

## Optimizations

- **Drop T006 and T008 from this phase** (defer with T019/T020). No chip surface without the record-panel waiver. Bound render later, at the panel, with N=25.
- **Spend the second hunk on refresh, not RelationLinks.** Merge inverse `sourcePaths` into `RelationRollupResult.targetPaths`, and return `sourceDatabaseIds` (or equivalent) so **both** `DatabaseView.buildRowsWithRelations` (`3348-3372`) and `EmbeddedDatabaseRenderer.buildRowsWithRelations` (`3190-3221`) register Expense paths **and** the Expenses database for `handleDataChangeBatch`. Prefer a tiny helper next to `buildRelationInverse` so the two view copies do not diverge.
- **Do not wait on 001.** Implement against the existing scan. If 001 already stored Reports-side “Expenses (R)” relations, local relation wins (`relationColumns.get` hits) and inverse is unused for those rollups — that is correct, not a conflict. New Report rollups that should invert Month links must **not** have a local column keyed `Month`.
- **Keep inverse out of `buildRelationRollups`’s early-return.** Call `buildRelationInverse` from inside the rollup loop only when a *specific* `relationField` misses locally **and** the function already passed the `:36` gate (viewed DB has rollup columns). That matches SC-002 rollup-only: no inverse work on DBs with zero rollups. Do **not** call `buildRelationRollups` from the inverse.
- **Resolution rule, no `types.ts`.** When local miss: find columns in `context.databases` with `column.key === config.relationField && column.type === "relation" && column.relationConfig.targetDatabaseId === context.sourceDatabase.id`. Feed those source records (the ones whose resolved link is the current Report row) into existing `aggregateRollup` (`92-129`). No new aggregation kinds. Local relation always wins if the key exists on the viewed DB.
- **Vitest bootstrap is shared with 007.** If 007 already added `src/__tests__/setup.ts`, 008 only adds `src/data/RelationInverse.test.ts` (and optionally `"test": "vitest run"`). Do not treat package.json as a feature call site.
- **`SYNC_WRITES_DEFAULT = false`** stays a module constant with **no write branch**. It is a compile-time tripwire, not a runtime flag.
