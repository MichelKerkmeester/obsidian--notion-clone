# Synthesis: Live Reports Roll-ups
> One-line: ranked Notion-parity enrichment for this feature, synthesized by Grok 4.6 (xhigh-fast) from the phase's 10 research iterations. Evidence trail: research.md.

## Verdict

Build this phase as **vault `database:` YAML only** — it is the highest-value Notion-parity win (Wave 0, effort S, value 5) because the fork already implements the exact four rollup kinds Reports need (`count` | `sum` | `avg` | `list`) as display-only derived values. Do **not** add a new `src/` module here: REQ-004 and plan §3 freeze TypeScript; EuroFormat is already the isolated display seam live SUMs will use. The single biggest risk is a **silent empty SUM**: rollups resolve only **forward** from the Reports row’s own relation column, and a wrong amount-property key or empty/mis-targeted relation is UI-indistinguishable from “no children” (`emptyRollupValue` → COUNT `0`, SUM `null`). Halt on the two spec UNKNOWNs (live amount keys, `db_view` paths) rather than guessing.

Feasibility: **likely** (config/row wikilinks; hard only if the operator refuses to maintain the Reports-side links and waits for a later inverse-relations phase). Fork files: **none**. Effort: **S**. Build-order: **first after locating `db_view` notes** (gates every rollup). Citation: `Obsidian Plugin/src/data/RelationRollup.ts:70-78`.

Bind only existing kinds: SUM related Expenses.cost, Sales.gross, Income.net and COUNT related children, using **ops-confirmed** YAML keys. Feasibility: **clear** once keys and Reports-side relations exist. Fork files: **none**. Effort: **S**. Build-order: **after item 1; blocked on ops keys**. Citation: `Obsidian Plugin/src/data/RelationRollup.ts:99-128` (count short-circuit; sum via `toChartNumber`; unknown kind falls through to sum — do not put median/min/max in YAML).

3. **Pin `computedSyncMode=display-only` on Reports** — Notion cannot write rollup values via the API; the fork already defaults to display-only, but `automatic` would `updateFrontmatter` computed keys and enqueue Report/child paths. A short-lived `list` column is the only in-product inventory of resolved children. Feasibility: **clear**. Fork files: **none**. Effort: **S**. ## Recommended build (locked design)

**Core algorithm (already in the fork — configure it, do not reimplement).** On each Reports view load, `buildRelationRollups` walks Reports rows, not children: for each rollup column it loads `rollupConfig.{relationField, targetField, aggregation}`, resolves the **Reports** relation’s wikilinks with `parseRelationValues` → `metadataCache.getFirstLinkpathDest`, keeps paths that exist in `databaseById.get(targetDatabaseId).recordsByPath`, dedups with `seenPaths`, then `aggregateRollup`: `count` → `records.length`; `list` → de-duped `stringifyValue`; `sum`/`avg` → `toChartNumber` (strict `Number()`, no wikilink digit scrape) then sum or `sum/length`; empty numeric set → `null`; nested rollup targets → `emptyRollupValue`. Output is `valuesByPath` only. Consumers: `DatabaseView.calculateRelationRollups` (`Obsidian Plugin/src/views/DatabaseView.ts:3388-3399`) and `EmbeddedDatabaseRenderer`; cells read `row.computed[col.key]` (`CellRenderer.ts:656`). Nested rollups are rejected in-fork and in Notion ([Help: “Can I rollup a rollup? Unfortunately not”](https://www.notion.com/help/relations-and-rollups)).

**Vault integration (this phase’s only mutation).** Child Expenses/Sales/Income: Month `relationConfig.targetDatabaseId` = Reports id; each row wikilinks its Report note. Reports: relation columns targeting those three databases (reuse Notion names such as Expenses (R)); rollup columns `sum`/`count` against ops-confirmed keys; `computedSyncMode: display-only`; optional `Snapshot*`. Do not bind footer `SummaryRenderer` kinds (`SUM`…`LATEST` in `SummaryRenderer.ts:19-22`) or chart `median|min|max|range|percent-*` as if they were relation rollups — a Reports-table footer SUM totals **all months**, which is the wrong question for a per-month Report note (`GroupDisplay.ts` has no per-group aggregation).

**EuroFormat isolated-module pattern — already shipped; add nothing under `src/` this phase.** `Obsidian Plugin/src/data/EuroFormat.ts:1-42` is the 42-line leaf (“Kept in one module so it stays a small, rebasable diff”). Live SUM/COUNT cells already hit that module with **zero new call sites**: `getColumnDisplayType` maps rollup `count|sum|avg` → `"number"` (`ColumnDisplay.ts:18-23`), `CellRenderer` switches on that type and `formatNumber` → `formatEuroNumber` (`CellRenderer.ts:13,255-262,2575-2576`). Footer chrome uses `formatEuroNumber2` (`SummaryRenderer.ts:7,551-556`). Currency **euro-sign** (`formatEuroCurrency` at `CellRenderer.ts:196-198`) does **not** apply to rollups: display type is hardcoded `"number"`, not `"currency"`. Accept nl-NL grouped numbers this phase; do not patch `ColumnDisplay.ts` (REQ-004).

**Successor module (locked on paper, not this diff):** `src/data/RollupAggPack.ts` — registry of `median|min|max|percent`, reuse `toChartNumber`, `optionEntries()` for the modal. Call sites: (1) `types.ts:44` widen `RollupConfig.aggregation`; (2) `RelationRollup.ts:123-128` replace the sum/avg tail and `emptyRollupValue` at `159-160`; (3) `RelationRollupConfigModal.ts:137,168-176` append pack options and extend the numeric-target gate. Preserve Anytype’s derive-at-render / no-persist pattern (`anytype-ts/src/ts/component/block/dataview/view/grid/foot/cell.tsx:44-49`), not AppFlowy’s recompute-and-store `format!("{:.2}")` strings (`appflowy/.../flowy-database2/src/services/calculations/service.rs` + `calculation_entities.rs:69-78`).

## Edge cases & mobile/iCloud safety

**Must handle (fork already defines the behavior; config must not fight it).** Empty Month / unresolved wikilink / path not in the target DB: skip the link; COUNT `0`, SUM/AVG `null` (empty placeholder, not a crash) — `RelationRollup.ts:72-74,99,126-128,159-160`; `RelationLinks.ts:23-25`. Report with zero children: same; note is not deleted. Wrong `targetDatabaseId`: `getTarget` returns null → empty rollup, no error (`RelationRollup.ts:43-49,64-66`) — treat as YAML bug. Duplicate wikilinks to one file: counted once per relation column (`seenPaths`). Two relation columns on the same Report that both point at the same children: each rollup counts independently. Non-numeric amount text: dropped from SUM; AVG uses numeric-only denominator (`ChartAggregation.ts:191-198`). Amount-key mismatch: silent empty/zero — **no fallback field**. Nested rollup as target: empty, matching Notion. Saved / Remaining: not derived (Income − Expenses is out of scope). Concurrent child edits: per-path `writeQueues` serialize the **child** files only (`DataSource.ts:88-120`); Report path must stay off the queue. Refresh after a child save: vault/metadata events coalesce on an **80ms** timer (`DataSource.ts:1938-1998`). Do not interpret SUM empty as `0` in acceptance unless the UI literally shows `0` (count does; sum does not).

**Why this is safe on mobile + iCloud (display-only, as the spec requires).** Rollups never write frontmatter (`types.ts:69`; `RelationRollup.ts` is a pure read). Under display-only, `syncComputedForFile` early-returns unless automatic (`EmbeddedDatabaseRenderer.ts:2834`; `DatabaseView.ts:10244,10389-10390`). The only enqueue sites are `mutateFrontmatter` and `updateViewDefFile` (`DataSource.ts:989-992`) — child amount edits queue the child path; they do not rewrite the Report note. Residual Report-file writes are **not** rollup recomputes: one-time scan migrations, and user-initiated view-config saves (debounced). Sole `require("electron")` is `ExportSaveTarget.ts` (export dialog), outside this path. `RelationRollup.ts` / `ComputedSync.ts` / `DataSource.ts` use cross-platform Obsidian APIs; `Platform.isMobile` gates UI chrome only. AppFlowy has no rollup primitive and no mobile-specific aggregation widgets; Anytype’s aggregates are client-side footer state and never synced — both support “derive at render, do not persist,” which this phase already matches. UNKNOWN (not disprovable from fork code): whether iOS `processFrontMatter` is atomic-replace; irrelevant while display-only keeps the Report path off the writer.

## Open questions / operator decisions

1. **Live amount/currency property keys** for Expenses / Sales / Income (spec names `cost` / `gross` / `net` are Notion-facing labels). Research cannot resolve them; a guessed key yields a plausible empty SUM. **Default: halt and ask ops; write UNKNOWN; do not bind.**

2. **Filesystem paths** of the Reports, Expenses, Sales, and Income `db_view` notes. **Default: inventory the live vault in Setup; do not invent paths.**

3. **Does each Report note already hold populated inverse relation wikilinks** (Reports.Expenses (R) and siblings), or only children hold Month? **Default: inventory Reports frontmatter; if empty, populate Reports-side wikilinks as part of this phase (still vault data). Do not wait for derived-inverse plugin work.**

4. **Keep `Snapshot*` columns?** **Default: yes** — capture screenshot-era Income/Expenses/Sales/Saved in Setup and show them beside live rollups (REQ-005). Explicit deferral is allowed only as an operator call.

5. **Saved live this phase?** **Default: no** — static or `Snapshot*` only (REQ-006); Remaining/Saved formulas belong to a later computed-fields phase.

6. **Ship extra Notion calculate functions (median/min/max/range/percent) now?** **Default: no** — successor pack 002 / `RollupAggPack`. YAML must not name kinds the union does not contain (unknown ids currently **sum**).

7. **Euro sign on rollup cells vs nl-NL number grouping?** **Default: accept `formatEuroNumber` grouping this phase**; euro-sign needs a fork display-type change, which REQ-004 forbids.

8. **Use table-footer `SummaryRenderer` as the monthly figure?** **Default: no** for per-month Report totals (it sums the whole Reports view). Optional as a year-to-date sanity bar only, after SC-001 passes.
