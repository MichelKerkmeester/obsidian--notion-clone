# Iteration 1: Fork Capability Baseline — Rollups, ComputedSync, Write Queues, Relation Resolution

## Findings

1. **Rollup kinds implemented today are exactly `count`, `list`, `sum`, `avg`** in `aggregateRollup()` of `data/RelationRollup.ts`. `count` short-circuits to `records.length` before any field lookup [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:87]; `list` builds a de-duplicated ordered array keyed by `stringifyValue(value)` [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:104-115]; `sum` and `avg` share one numeric path ending `return aggregation === "avg" ? sum / numbers.length : sum` [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:122-123]. No other aggregation kind exists; an unknown kind falls through to `sum`.

2. **Missing / non-numeric handling in sum/avg is strict-numeric via `toChartNumber`**: values that are `null`, empty string, or non-numeric strings map to `null` and are filtered out (`numbers = values.map(toChartNumber).filter(...)`); if no numeric values remain the rollup returns `null`; there is NO coercion of wikilink text into digits anymore — a code comment documents the old bug ("原先 Number(replace(/[^0-9.-]/)) 会从笔记名/wikilink 随意提取数字（[[Task 42]]→42）... 改用 toChartNumber") [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:117-121]. `toChartNumber` itself: finite numbers pass through, non-empty strings must parse with `Number()`, everything else → `null` [SOURCE: Obsidian Plugin/src/data/ChartAggregation.ts:191-198]. Empty relation set therefore yields count=0 / list=[] / sum=avg=null (also see `emptyRollupValue`: `aggregation === "count" ? 0 : aggregation === "list" ? [] : null`) [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:126-128].

3. **Nested rollups as rollup targets are explicitly rejected**: if the target column's type is `"rollup"`, `aggregateRollup` returns `emptyRollupValue(aggregation)` instead of aggregating [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:88-89]. Target field resolution supports file fields (`isFileFieldKey`), computed columns (evaluated per-record via `evaluateComputedFields`), else raw frontmatter [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:132-152].

4. **ComputedSyncMode has exactly three modes**: `"automatic" | "display-only" | "manual"` defined in `data/types.ts:111` (`export type ComputedSyncMode = "automatic" | "display-only" | "manual";`). `display-only` is the DEFAULT: `DEFAULT_COMPUTED_SYNC_MODE: ComputedSyncMode = "display-only"` and `normalizeComputedSyncMode` coerces anything not automatic/manual back to display-only [SOURCE: Obsidian Plugin/src/data/ComputedSync.ts:3,20-25]. New databases created from parsed sources hard-code `computedSyncMode: "display-only"` [SOURCE: Obsidian Plugin/src/main.ts:1580].

5. **Display-only enforcement is read-side gating of every property write-back, not a renderer flag**: `PropertyTypeConflict.ts:114` skips observable property-type registration entirely when `syncMode === "display-only"` (`if (syncMode === "display-only") continue;`) [SOURCE: Obsidian Plugin/src/data/PropertyTypeConflict.ts:113-114]. Column operations gate saved-property rename/delete/cleanup behind `!displayOnly` (`isDisplayOnlyComputedSync()` at views/ColumnOperations.ts:1003-1005 returns `normalizeComputedSyncMode(...) === "display-only"`; used at lines 136-137, 304, 341, 814-817) [SOURCE: Obsidian Plugin/src/views/ColumnOperations.ts:1003-1004]. Switching away from display-only requires confirmation for `automatic` [SOURCE: Obsidian Plugin/src/views/ViewConfigPanelRenderer.ts:1326-1333]. UI copy states the contract: display-only means "Formula values are visible in the database, but do not create or update note properties." [SOURCE: Obsidian Plugin/src/i18n.ts:807-808]. The actual bulk write-back executor lives outside these files (invoked on mode change at DatabaseView.ts:5600-5607 where leaving sync resets `db.computedSyncMode = "display-only"`) — its exact file/function is UNKNOWN from this iteration's reads.

6. **`DataSource.writeQueues` is a per-path promise chain Map**: `private writeQueues = new Map<string, Promise<void>>();` with comment "Per-file write queue to serialize processFrontMatter calls on the same file" [SOURCE: Obsidian Plugin/src/data/DataSource.ts:88-89]. The single choke point `enqueueWrite(path, ...)` chains onto the previous promise for that exact path, swallows prior errors so the queue never poisons, marks ownership, and self-cleans when it is the chain tail [SOURCE: Obsidian Plugin/src/data/DataSource.ts:99-120].

7. **Exactly two call sites enqueue writes**, both private methods on DataSource: `mutateFrontmatter(file, mutator, context)` → `this.enqueueWrite(file.path, ...)` wrapping `app.fileManager.processFrontMatter` for note frontmatter mutations [SOURCE: Obsidian Plugin/src/data/DataSource.ts:289-293], and `updateViewDefFile(...)` for view-definition config files with comment "Serialized per-file to prevent conflicts with concurrent frontmatter writes" [SOURCE: Obsidian Plugin/src/data/DataSource.ts:990-992]. So note-write enqueueing is exclusively via `mutateFrontmatter` (all cell edits, computed save-backs, etc.).

8. **Proof rollup computation never enqueues a parent/report-path write**: `buildRelationRollups` is pure — it only reads frontmatter/metadataCache and returns `{ valuesByPath, targetPaths }` maps; it contains zero calls to DataSource write APIs [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:24-84]. Its only consumers build derived rows: DatabaseView.calculateRelationRollups passes results into view rendering [SOURCE: Obsidian Plugin/src/views/DatabaseView.ts:3388-3403]; EmbeddedDatabaseRenderer assigns `derived = result.valuesByPath` and feeds `rowPipeline.build(records, ...)` plus caches target paths for refresh scoping [SOURCE: Obsidian Plugin/src/views/EmbeddedDatabaseRenderer.ts:3196-3219]. Type contract agrees: "Rollups are display-only derived values and are never written to frontmatter." [SOURCE: Obsidian Plugin/src/data/types.ts:69]. CellRenderer renders rollups read-only: `if (col.type === "rollup") return row.computed[col.key]` with double-click opening config modal, not editing [SOURCE: Obsidian Plugin/src/views/CellRenderer.ts:656, 425-431, 459-465].

9. **Relation targets resolve by wikilink parse + vault linkpath resolution + targetDatabaseId scoping**: relation cells store native Obsidian wikilinks in frontmatter [SOURCE: Obsidian Plugin/src/data/types.ts:67-68]. `parseRelationLink` matches strict full-string `[[target#subpath|alias]]` syntax, strips subpath after `#` for the target, keeps alias [SOURCE: Obsidian Plugin/src/data/RelationLinks.ts:5-22]; `parseRelationValues` accepts string or array, dropping unparseable entries silently [SOURCE: Obsidian Plugin/src/data/RelationLinks.ts:24-26]. Only columns with `column.type === "relation" && column.relationConfig?.targetDatabaseId` become rollup inputs; each link resolves via `app.metadataCache.getFirstLinkpathDest(link.target, sourceRecord.file.path)`, then the resolved path must exist in the target database's record map (`target.recordsByPath.get(resolved.path)`) built from `databaseById.get(targetDatabaseId)` [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:30-35, 55-70]. Deduplicated per-source-row via `seenPaths` [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:72-83].

10. **Broken/empty relations degrade to empty rollups, never errors**: missing `relationConfig.targetDatabaseId`, unknown database id, unresolved linkpath (`getFirstLinkpathDest` null), or path not in target database records → the link is skipped; if no links survive, `aggregateRollup([]...)` yields count=0, list=[], sum/avg=null [SOURCE: Obsidian Plugin/src/data/RelationRollup.ts:57-59, 63-66, 87-89, 126-128].

11. **Rollup value rendering consumers**: table cell renderer (`CellRenderer.ts` rollup branches above), embedded-database rows (`EmbeddedDatabaseRenderer.ts:3196-3219`), and main DatabaseView pipeline (`DatabaseView.ts:3388-3403`). Additional rollup-aware UI surfaces exist but were not line-audited this iteration: SummaryRenderer, BoardRenderer, GalleryRenderer, ListRenderer, CalendarTimelineRenderer, RecordDetailPanel, ToolbarRenderer (file-level match only) [SOURCE: grep -l "rollup" src/views → 20 files matched].

# Iteration 2: Notion Rollup Behavior via Official Docs & Web Research

## Findings

1. **Notion's rollup config model is a 4-tuple: relation property + target property + calculate function + display formatting.** The official Help Center: clicking a rollup cell asks for (a) the relation property to roll up, (b) the property of those related pages, (c) "the calculation you want to apply", plus (d) "the number formatting you want to display" and (e) "the decimal point placement you want to set" [SOURCE: https://www.notion.com/help/relations-and-rollups]. The API schema mirrors it exactly: `rollup` type object has `function` (enum), `relation_property_id`, `relation_property_name`, `rollup_property_id` (id of the property being rolled up), `rollup_property_name` [SOURCE: https://developers.notion.com/reference/property-object].

2. **Canonical calculate-function enum (API):** `average, checked, count, count_per_group, count_values, date_range, earliest_date, empty, latest_date, max, median, min, not_empty, percent_checked, percent_empty, percent_not_empty, percent_per_group, percent_unchecked, range, show_original, show_unique, sum, unchecked, unique` [SOURCE: https://developers.notion.com/reference/property-object; repeated at https://developers.notion.com/reference/page-property-values]. This maps onto the fork's current four kinds (`count, list, sum, avg`) as: `count→count`, `list→show_original/show_unique`, `sum→sum`, `avg→average`; the remaining ~20 are parity gaps.

3. **UI Calculate option groups and their gating (official):** general options — `Show original` ("just shows all related pages in the same cell. It's the same as the relation property itself"), `Show unique values`, `Count all` (total values incl. empties), `Count values` (non-empty), `Count unique values`, `Count empty` (pages with empty target value), `Count not empty`, `Percent empty`, `Percent not empty`. Numeric-only (only available for Number properties): `Sum, Average, Median, Min, Max, Range` (Range = Max − Min). Date-only: `Earliest date, Latest date, Date range`. Checkbox variants (`Percent checked/unchecked`, `Count checked/unchecked`) exist in the API enum under names `checked, unchecked, percent_checked, percent_unchecked` [SOURCE: https://www.notion.com/help/relations-and-rollups; enum SOURCE: https://developers.notion.com/reference/property-object].

4. **Sorting constraint:** "Rollups can only be sorted when they output a numeric value" [SOURCE: https://www.notion.com/help/relations-and-rollups] — relevant to any future sort support in the plugin's table/board views.

5. **Crumbs #4 — rollups are derived-at-read, never stored as page data.** Three independent official statements: (a) page property value doc: the rollup value object carries "The value of the calculated rollup. The value can't be directly updated via the API" and "The API does not support updating rollup page property values. To change a page's rollup property, use the Notion UI" [SOURCE: https://developers.notion.com/reference/page-property-values]; (b) the value type is dynamic (`array | date | incomplete | number | unsupported`), including a transient `incomplete` state meaning the calculation has not finished yet [SOURCE: https://developers.notion.com/reference/page-property-values]; (c) a size guard: if the API "can't calculate a rollup because it depends on too many related pages or nested formulas and rollups, rollup.type is set to `unsupported`… no partial value", and rollups with >25 references must be fetched via the dedicated Retrieve-a-page-property endpoint [SOURCE: https://developers.notion.com/reference/page-property-values]. Together these prove server-side computation at read time (with an async/cache layer and compute limits), NOT persistence into page storage — direct validation of the fork's display-only design where "Rollups are … never written to frontmatter."

6. **Computation model is live-but-async:** third-party analysis: "The calculation engine runs in the background and updates the rollup value whenever the source data changes," and cells can display a literal "Calculating" placeholder when the engine cannot finish (circular references, hundreds/thousands of related rows, corrupted relation metadata) [SOURCE: https://wisechecker.com/fix-notion-rollup-calculation-stuck-on-calculating-indicator/]. Consistent with the API's `incomplete` type above — i.e., reactive recompute with eventual consistency, not lazy-on-open only, not eager write-through.

7. **Empty-relation / non-numeric behavior:** official docs do NOT explicitly state what Sum displays with zero related rows (UNKNOWN from primary sources). Best available evidence: third-party FAQ — "why is my rollup blank? most common causes are: the relation has no linked pages, you picked the wrong property, or the rollup is calculating something that does not apply (for example, 'sum' on text)" [SOURCE: https://www.notionventured.com/blog/notion-relations-rollups-explained] ⇒ Notion renders blank/nothing (not 0) for empty relations and non-applicable aggregations. This matches the fork's `emptyRollupValue` returning `null` for sum/avg on empty sets [INFERENCE: based on iteration-001 finding 2 and the blank-rollup behavior above].

8. **Nested rollups are prohibited in Notion too:** "Can I rollup a rollup? Unfortunately not, as this could create unintended loops." [SOURCE: https://www.notion.com/help/relations-and-rollups] — independently validates the fork's hard rejection of rollup-type targets in `aggregateRollup` (iteration-001 finding 3). The API's `unsupported` guard also cites "nested formulas and rollups" as a compute-limit trigger [SOURCE: https://developers.notion.com/reference/page-property-values].

9. **Aggregate rollups (column-level summaries) are a separate feature:** tables and boards let you hover a column → "Calculate → More options" → e.g. Sum across the whole database [SOURCE: https://www.notion.com/help/relations-and-rollups] — distinct from row-level rollup config and relevant to SummaryRenderer scope decisions.

# Iteration 3: AppFlowy Rust Database Model — Aggregations vs Roll-ups

## Findings

1. **AppFlowy has no "roll-up" concept at all; its closest primitive is per-field "calculations"** (view-level column summaries). The full aggregate taxonomy is `enum CalculationType { Average = 0, Max = 1, Median = 2, Min = 3, Sum = 4, Count = 5, CountEmpty = 6, CountNonEmpty = 7 }` [SOURCE: specs/obsidian/002-note-db-notion-parity-build/context/appflowy/frontend/rust-lib/flowy-database2/src/entities/calculation/calculation_entities.rs:69-78]. A repo-wide case-insensitive grep for `rollup|Rollup` across flowy-database2 returned zero matches (negative result, see Tried/Ruled out).

2. **Calculations are strictly same-view, single-field**: the wire/entity shape `CalculationPB` carries only `{id, field_id, calculation_type, value}` [SOURCE: .../flowy-database2/src/entities/calculation/calculation_entities.rs:12-22]. There is no reference to another field, another view, or another database — so AppFlowy does NOT support Notion-style cross-database relation roll-ups. Parity claim: AppFlowy ≈ Notion's per-column footer statistics only, not its Rollup property.

3. **Numeric aggregates are restricted to `FieldType::Number` cells only**, excluding even Relation fields: `CalculationType::is_allowed` matches `Max|Min|Average|Median|Sum` against `matches!(field_type, FieldType::Number)` and returns true unconditionally only for `Count` [SOURCE: .../flowy-database2/src/entities/calculation/calculation_entities.rs:121-140]. Since `Relation = 10` exists as a field type [SOURCE: .../flowy-database2/src/entities/field_entities.rs:427-444], relations can be stored but never aggregated.

4. **Cross-database structure exists at the relation layer, but nothing computes over it**: `pub struct RelationTypeOptionPB { pub database_id: String }` points at a foreign database [SOURCE: .../flowy-database2/src/entities/type_option_entities/relation_entities.rs:45-48], and relation edits are row-id sets (`RelationCellChangeset { inserted_row_ids, removed_row_ids }` [SOURCE: .../flowy-database2/src/services/field/type_options/relation_type_option/relation_entities.rs:4-7]). UNKNOWN: whether any higher layer (Dart frontend) computes derived values from relation cells; nothing in flowy-database2 does.

5. **Computation is recompute-on-demand with rayon, not incremental**: `CalculationsService::calculate` dispatches to `calculate_average/max/median/min/sum/count*`, each pulling cell values through the type-option handler (`handle_numeric_cell`, `handle_is_empty`) and reducing in parallel (`cells.par_iter()...reduce`) [SOURCE: .../flowy-database2/src/services/calculations/service.rs:14-113]. Cells arrive wholesale via the delegate `get_cells_for_field(view_id, field_id)` [SOURCE: .../flowy-database2/src/services/calculations/controller.rs:19-21], i.e., all rows of that one view are refetched and reduced whenever the task scheduler fires (`src/services/calculations/task.rs:31`). For Live Reports parity this means O(rows × recalcs) cost per keystroke unless the fork adds caching/dirty-tracking.

6. **Results are persisted as preformatted strings, decoupled from number/currency formatting**: computed values are hard-formatted with `format!("{:.2}", ...)` (fixed 2 decimals) [SOURCE: .../flowy-database2/src/services/calculations/service.rs:31,45,57,70,83] and stored back via `update_calculation(view_id, calculation)` on the delegate trait [SOURCE: .../flowy-database2/src/services/database_view/view_calculations.rs:71-73], which routes into collab persistence (`async fn update_calculation` declared in `view_operation.rs:93`). Meanwhile currency/scale live separately in `NumberTypeOptionPB { format: NumberFormatPB, scale: u32, symbol: String }` with `USD = 1 … Percent = 36` [SOURCE: .../flowy-database2/src/entities/type_option_entities/number_entities.rs:6-18,46,80] — calculation values ignore this formatting entirely. A fork wanting Notion-style currency-formatted roll-ups must apply NumberFormat at display time, not trust the stored string.

7. **Storage model**: definitions (which calculations exist per view) persist in collab view data; values are cached in-memory (`AnyTypeCache`, `CalculationsByFieldIdCache` [SOURCE: .../flowy-database2/src/services/calculations/controller.rs:33-40]) and rewritten after each recompute. So: definition = stored, value = recomputed-then-stored (last-write snapshot, no history).

8. **The `Summary` field type (=11) is AI text summarization, not numeric roll-up** — it pairs with `Translate`; neither participates in `CalculationType::is_allowed` numeric paths [SOURCE: .../flowy-database2/src/entities/field_entities.rs:440-441; .../src/entities/calculation/calculation_entities.rs:121-140].

# Iteration 9: EuroFormat isolated-module precedent → RollupAggPack fork-integration design

## Findings

1. **The EuroFormat precedent is a 42-line leaf module owning exactly one concern (nl-NL number/currency rendering) and integrating through only two files / five lines.** The module owns three private `Intl.NumberFormat` instances (`nlNumber`, `nlNumber2`, `nlEuro`) and exports three pure functions: `formatEuroNumber(value)` (≤6 fraction digits, plain cells), `formatEuroNumber2(value)` (≤2 digits, footer summaries), `formatEuroCurrency(value)` (euro-sign currency cells). All three return `"-"` for non-finite input. Its header states the fork-integration contract verbatim: *"Local fork override. Kept in one module so it stays a small, rebasable diff."* [SOURCE: Obsidian Plugin/src/data/EuroFormat.ts:1-42]

2. **The complete EuroFormat call-site surface is 5 lines across 2 files** — `views/CellRenderer.ts:13` (`import { formatEuroNumber, formatEuroCurrency } from "../data/EuroFormat"`), applied at `views/CellRenderer.ts:198` (currency cells: `td.textContent = isNaN(num) ? "-" : formatEuroCurrency(num)`) and `views/CellRenderer.ts:2576` (`return formatEuroNumber(value)`), plus `views/SummaryRenderer.ts:7` (`import { formatEuroNumber2 }`) applied at `views/SummaryRenderer.ts:556`. No other file references it (repo-wide grep found zero additional hits). Rebase safety comes from three properties: (a) the module is purely additive — a new file upstream never conflicts with; (b) each call site replaces a stock formatting expression at a *stable seam* (a display-formatting chokepoint, not business logic); (c) functions are pure and dependency-free, so upstream refactors around them rarely touch the seam lines. [SOURCE: Obsidian Plugin/src/views/CellRenderer.ts:13,198,2576; SOURCE: Obsidian Plugin/src/views/SummaryRenderer.ts:7,556; INFERENCE: stability properties derived from the seam locations and the module's own stated intent]

3. **Rollup aggregation is currently a closed 4-value union declared at one line**: `data/types.ts:44` — `aggregation: "count" | "sum" | "avg" | "list";` inside `RollupConfig`. The richer numeric kinds exist today **only** in the chart/footer world: `ChartAggregation` includes `"median" | "min" | "max" | "range" | "percent-*"` etc. at `data/types.ts:179-194`, gated by `isNumericAggregation`-style logic in `data/ChartAggregation.ts:141` (`return aggregation === "sum" || aggregation === "avg" || aggregation === "median" || ...`). [SOURCE: Obsidian Plugin/src/data/types.ts:44,179-194; SOURCE: Obsidian Plugin/src/data/ChartAggregation.ts:141]

4. **The entire rollup-compute pipeline funnels through one function**, `aggregateRollup()` in `data/RelationRollup.ts` (~line 100): `count` short-circuits to `records.length`; `list` dedups via `stringifyValue`; sum/avg share a tail that maps values through `toChartNumber` (already imported from `./ChartAggregation`) then computes `sum / numbers.length` or `sum`. Empty-value semantics live in `emptyRollupValue()` (`count→0, list→[], else null`). Nested-rollup targets are rejected (`if (column?.type === "rollup") return emptyRollupValue(aggregation)`). Results are returned as `valuesByPath` from `buildRelationRollups()` and consumed read-only by renderers — e.g. `views/CellRenderer.ts:656` (`if (col.type === "rollup") return row.computed[col.key]`) — never written to frontmatter, which is the existing display-only guarantee. Footer-summary participation is separately gated in `views/SummaryRenderer.ts:77-79` to `count | sum | avg` only. [SOURCE: Obsidian Plugin/src/views/modals/RelationRollupConfigModal.ts:109,137,168-176,246; SOURCE: Obsidian Plugin/src/views/SummaryRenderer.ts:77-79]

   - **What the module owns** (`data/RollupAggPack.ts`, new leaf file): a registry of extension aggregations, e.g. entries `{ id: "median"|"min"|"max"|"percent", numeric: true, emptyValue: null, compute(numbers: number[]): number }` implementing pure math reusing the already-imported `toChartNumber` coercion convention from `ChartAggregation.ts`; plus `optionEntries()` returning i18n-keyed dropdown options (reusing existing `chart.medianAggregation` / `chart.minAggregation` / `chart.maxAggregation` keys already present in `ChartViewModel.ts:41-43`).
   - **Call-site edit 1** — `data/types.ts:44`: widen the union to include the packed ids (one line).
   - **Call-site edit 2** — `data/RelationRollup.ts` sum/avg tail (~lines 119-127): replace the inline `aggregation === "avg" ? sum/length : sum` expression with `RollupAggPack.resolve(aggregation, numbers)` which handles the packed kinds and falls back to stock sum/avg; and delegate `emptyRollupValue()`'s else-branch to the pack (one adjacent line).    - **Call-site edit 3** — `views/modals/RelationRollupConfigModal.ts:170-173`: append `...RollupAggPack.optionEntries()` after the four stock options and extend the line-137 numeric gate to consult `pack.numeric`. One contiguous block.

   - **Rebase safety**: identical mechanism to EuroFormat — additive leaf module, pure functions, single-expression seams at stable chokepoints (the union line, the compute tail, the dropdown array). Upstream changes to chart code or other renderers cannot conflict.
   - **Display-only guarantee preserved**: packed aggregations are computed inside `buildRelationRollups()` whose output lands only in `row.computed` (read at `CellRenderer.ts:656`); no new write path is introduced, consistent with iteration 7's finding that display-only derivation triggers zero vault writes. Percent additionally stays a pure ratio of already-collected values (no extra source reads). [INFERENCE: based on findings 3-5 and lineage iteration-007 display-only write-path analysis]
