# Iteration 09 — Micro-interactions and feedback

## Focus

Iteration 9 of 10 for the `codex-luna` track. This pass focuses on feedback that tells a user what an interaction is doing and whether it finished: hover, drag/reorder, inline edit, selection, loading, empty, and error.

The new angle is lifecycle ownership. The plugin has many good one-frame cues—drop shadows, editing borders, selection classes, a refresh spinner—but several cues are timer-owned or disappear before the asynchronous operation settles. A useful interaction vocabulary here is `intent → pending → committed → failed`, with `stale → refreshing → ready` for data. The visual should follow the logical record/cell identity, not the lifetime of a DOM node or a short timeout.

Research snapshot: 2026-08-27. Prior iterations were read in full; broad empty-state normalization, overlay semantics, stable grid structure, object detail, calendar overflow, and cross-view movement meaning are intentionally not repeated below.

## Current-UI findings (file:line)

1. **Sort reordering shows a target, but not the insertion result.** `SortPanelRenderer` adds a generic `is-drop-target` while a rule is dragged (`src/views/SortPanelRenderer.ts:94-110`) and calculates before/after only at drop time (`src/views/SortPanelRenderer.ts:195-217`). It then mutates the rule list, saves, and rebuilds the panel (`src/views/SortPanelRenderer.ts:219-235`). The table path already resolves before/after placement during drag (`src/views/TableRenderer.ts:684-712`), so sort rules and rows currently teach different confidence levels for the same gesture.

2. **Drop-zone feedback has a shorter lifetime than the drag operation.** Board group feedback is a 900 ms transient class (`src/views/BoardRenderer.ts:929-951`). A user can hold a card over a lane, pause, and lose the destination highlight while still dragging. Board movement is asynchronous (`src/views/BoardRenderer.ts:866-894`), but the renderer has no pending/committed/failed visual state to take over after `drop`. Table, gallery, and list drops also clear their target feedback before their async move completes (`src/views/TableRenderer.ts:697-712`, `src/views/GalleryRenderer.ts:365-401`, `src/views/ListRenderer.ts:365-401`).

3. **Editing and feedback are partly timer-owned.** Date segment editing marks a cell as editing for 1.6 seconds (`src/views/CellRenderer.ts:1362-1365`), and the generic input mount repeats the transient-class pattern (`src/views/CellRenderer.ts:2387-2394`). The helper removes classes on a timeout (`src/views/CellRenderer.ts:2454-2475`), although text editing can remain open until blur or Enter (`src/views/CellRenderer.ts:1950-1998`). The blue editing border therefore cannot reliably mean “this editor is active”; it can expire while the user is still typing.

4. **There are two cell-selection truths.** `CellRenderer.selectCell` clears `.db-cell-selected` in every database container and reapplies it for only 1.2 seconds (`src/views/CellRenderer.ts:823-828`). The durable range/focus selection is held separately by `DatabaseView` (`src/views/DatabaseView.ts:4273-4338,4432-4462`). CSS also treats them as different inputs: the fill handle depends on `.db-cell-selected` (`styles.css:4988-4991`), while range and focus use `.db-cell-range-selected` and `.db-cell-focus` (`styles.css:5003-5019`). A cell can remain selected in the action model while its most useful affordance has visually vanished; an embedded database can also clear a selection cue belonging to another container.

5. **Selection changes rebuild the action surface and close editing.** The dashboard removes and recreates the status bar on every render and closes the bulk editor first (`src/views/DatabaseView.ts:7010-7019`); the count is then created as an ordinary span (`src/views/DatabaseView.ts:7021-7035`) with no live-region contract. Embedded tables repeat the remove-and-rebuild path (`src/views/EmbeddedDatabaseRenderer.ts:3578-3597`). A selection drag, range extension, or refresh can therefore discard focus, the action anchor, and an in-progress bulk-edit context even when the logical selection is still valid.

6. **Refresh state is available but only painted on the toolbar.** `RefreshCoordinator` already distinguishes queued paths, unknown changes, and active refresh (`src/data/RefreshCoordinator.ts:47-84,113-148`). `ToolbarRenderer` maps that to a spinner and badge (`src/views/ToolbarRenderer.ts:307-329`), but the result surface is not marked busy. A full refresh removes result roots—including the selection bar—before rendering again (`src/views/DatabaseView.ts:10631-10648`); the embedded result path also removes the old surface before reading and turns a read exception directly into a generic empty block (`src/views/EmbeddedDatabaseRenderer.ts:941-957`). The user cannot tell “old data is being refreshed” from “there are no records” during the transition.

7. **Async moves have no renderer-local outcome identity.** Several drop handlers use `void` on a move promise after clearing the target (`src/views/TableRenderer.ts:697-712`, `src/views/GalleryRenderer.ts:365-401`, `src/views/ListRenderer.ts:365-401`), while board movement handles group-field updates and ordering in one async method (`src/views/BoardRenderer.ts:866-894`). Even if the lower-level action emits a notice, the result is not anchored to the moved record or destination, so a slow iCloud file update can leave the user unsure which reorder succeeded.

8. **Rerender can erase a hover/focus affordance without a pointer transition.** Table patching replaces changed row elements (`src/views/TableRenderer.ts:194-239`), and a full refresh removes all result roots (`src/views/DatabaseView.ts:10639-10646`). Row drag handles and empty-value hints are mostly hover/focus CSS (`styles.css:5045-5076,5136-5143`). If a row is replaced under a stationary pointer, the user gets no new `mouseenter` and may lose the action reveal; if the replaced node owned focus, keyboard users lose the same state even though the file path still exists.

## Anytype/AppFlowy patterns

- **AppFlowy gives row interaction one stable home.** Its Grid documentation puts row actions, row reordering, and whole-row selection on the row-number gutter ([Grid View, rows](https://appflowy-io-appflowy.mintlify.app/core/grid-view)). This is stronger than making each operation discoverable through a different transient target: one logical row anchor can own hover, focus, pressed, pending, and failure states. It also makes the manual-order rule explicit: adding a sort overrides manual ordering ([Grid View, reordering rows](https://appflowy-io-appflowy.mintlify.app/core/grid-view#reordering-rows)).

- **AppFlowy documents a compact typed edit contract.** Text fields support click or double-click, Enter confirms, and Escape cancels; select fields close on outside click or Enter; checkboxes support click or Space; complex fields use a popup ([Grid View, inline editing](https://appflowy-io-appflowy.mintlify.app/core/grid-view#inline-editing)). The valuable pattern is not the exact shortcut set; it is that commit, cancel, and typed-editor escalation are explicit and consistent. That gives an asynchronous save somewhere to show pending or failure without guessing whether blur meant “save and close.”

- **AppFlowy treats the grid as a live projection.** Its database documentation says Grid, Board, and Calendar are multiple views over the same rows and that a change in one view updates the others ([Databases](https://appflowy-io-appflowy.mintlify.app/core/databases)). For this plugin, the transferable feedback pattern is a small cross-view operation status tied to a stable path, not a transient highlight tied to one renderer.

- **Anytype’s frontend architecture separates interaction responsibilities.** Its public library map names dedicated `focus`, `preview`, `animation`, `scrollOnMove`, and `reactionScheduler` utilities ([Anytype frontend library map](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/lib/README.md)). The useful lesson is to centralize focus restoration, drag auto-scroll, animation timing, and rerender scheduling instead of letting each card/table editor invent a timeout. The public release log also records real inline-blur and loading/selection regressions ([Anytype releases](https://github.com/anyproto/anytype-ts/releases)); the product lesson is to test the transition between edit intent, persistence, and rerender as a first-class state.

- **Notion makes hover reveal contextual, but keeps the action model legible.** Its table guidance describes a row-hover checkbox for bulk selection, a row drag grip, direct property-value editing, and a menu for selected-row property changes ([Notion tables](https://www.notion.com/help/tables)). The pattern worth adopting is a quiet desktop reveal with an always-recoverable keyboard/touch path, followed by an action surface that stays attached to the selected set rather than vanishing after the pointer leaves.

- **Notion separates view settings from transient interaction.** Its view documentation treats layout, property visibility, filter, sort, group, and subgroup as current-view state ([Notion views, filters, and sorts](https://www.notion.com/help/views-filters-and-sorts)). Applied to feedback, this argues for showing a sort-blocked reorder explanation or a stale-refresh status as view state, rather than making users infer it from a disabled or disappearing cursor.

## Open threads for later iterations

- Define a reduced-motion contract for drag previews, refresh spinners, and success/failure transitions, including whether a non-animated status marker is required when `prefers-reduced-motion` is active.
- Test the interaction state machine against external iCloud changes arriving during inline edit, selection drag, reorder, split-pane activation, and hidden-view refresh; decide which state wins when the logical path disappears.
- Decide whether operation results belong in one shared in-view rail or in per-record anchors. A shared rail is simpler, but a per-record result marker may be better when several moves are queued.
