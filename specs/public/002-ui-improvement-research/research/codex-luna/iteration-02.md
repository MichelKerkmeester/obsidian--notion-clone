# Table / grid view research — iteration 02

## Focus

The table/grid is the primary surface for scanning, comparing, editing, and restructuring records. This iteration focuses on the grid’s information architecture and affordances: column headers, cells, row actions, selection, sorting, filtering, grouping, and calculations. The goal is to make the existing capabilities discoverable and predictable without adding note-body mutations, telemetry, or a second data model.

This is a deeper pass than iteration 01. It deliberately concentrates on table-specific failure modes: a changing column schema after filtering, actions that exist only in invisible hover/context-menu states, group sections that behave like separate tables, and summaries that are spatially detached from the columns they describe.

## Current-UI findings (file:line)

1. **Filtering can change the apparent schema.** `getVisibleColumns` auto-hides ordinary fields when none of the currently supplied `rows` has a value (`src/data/ColumnConfig.ts:92-117`). The table render receives the pipeline’s result rows (`src/views/DatabaseView.ts:6406-6432`), so a filter that leaves only records without a value in a field can make that column disappear; clearing the filter makes it return and can move every later column. Explicitly ordered or manually shown columns are protected, but the default schema is not stable.

2. **Header actions are not reliably available on touch or keyboard.** The controller installs sorting, a context menu, resize, and desktop drag-reorder (`src/views/ColumnHeaderController.ts:21-34`), but the menu trigger is literal `...` text (`src/views/ColumnHeaderController.ts:36-47`) and CSS hides it with both opacity and pointer-events until the header is hovered (`styles.css:4177-4208`). Resize and drag handles are also desktop-only (`src/views/ColumnHeaderController.ts:49-141`; `styles.css:15494-15506`). On a phone there is no hover state to reveal the header menu; on desktop, an invisible trigger is poor keyboard feedback.

3. **Sort state is visually compact but semantically incomplete.** A header shows a text arrow and, for multi-sort, a numeric suffix (`src/views/TableRenderer.ts:422-464`). Narrow columns hide the sort indicator unless the header is hovered (`styles.css:4210-4223`), and the `th` does not expose an `aria-sort` state. Users can therefore miss an active secondary rule or mistake a plain arrow for a one-click toggle.

4. **Header click is destructive to an existing multi-sort.** `sortByColumn` replaces the rules with one ascending rule unless there is exactly one existing rule; it then cycles ascending, descending, and cleared (`src/views/DatabaseView.ts:10220-10241`). The embedded renderer has the same behavior (`src/views/EmbeddedDatabaseRenderer.ts:2199-2218`). Multi-sort is available in the separate sort panel, but a quick header action cannot append a rule or preserve the current sort stack.

5. **Cells have a strong capability gap between what they do and what they communicate.** Normal cells select on single click and edit on double click (`src/views/CellRenderer.ts:409-430`); the keyboard layer already supports Enter, F2, Tab, arrows, and range operations (`src/views/DatabaseView.ts:1430-1558`; `src/data/TableKeyboardNavigation.ts:29-82`). Empty values are rendered as a visually transparent placeholder that appears mainly on editable-cell hover (`src/views/CellRenderer.ts:183-204`; `styles.css:5131-5143`). The result feels passive on touch and does not teach a new user that the grid is editable or keyboard-operable.

6. **Row operations are discoverable mainly through a context menu.** `RowMenu` attaches only a `contextmenu` listener to the row (`src/views/RowMenu.ts:30-40`). The existing desktop drag handle and mobile move button are separate, conditional affordances (`src/views/TableRenderer.ts:501-530,632-713`; `styles.css:5044-5084,15554-15636`), while open/duplicate/delete/insert actions have no stable row anchor. This is especially costly for touch users and for rows inside a collapsed group.

7. **Collapsed groups have no local selection affordance.** Group headers show collapse, label, count, and summaries (`src/views/TableRenderer.ts:122-150`), but the selection checkbox is created only in a table header (`src/views/TableRenderer.ts:422-432`). A user cannot select a group’s visible records while it is collapsed without expanding it and selecting rows individually. The existing range-selection machinery can represent the needed set (`src/views/RangeSelection.ts:1-51`; `src/views/DatabaseView.ts:4233-4271`).

8. **Grouped mode renders repeated independent grids.** Each group creates its own `.db-table-wrap`, table, header, and body (`src/views/TableRenderer.ts:157-190`). The patch path then relies on a group header being followed by that sibling table (`src/views/TableRenderer.ts:241-313`), and grouped sticky headers need a separate vertical offset (`styles.css:6281-6288`). This preserves local headers but makes horizontal scanning, column alignment, and “one grid” mental models harder—particularly with many groups.

9. **Calculations are detached from the columns they summarize.** The top summary is a horizontal list containing total and summary items (`src/views/SummaryRenderer.ts:164-209`), while group summaries are embedded in the group label area (`src/views/SummaryRenderer.ts:133-162`). Neither is an aligned footer beneath the relevant field. The table already has a shared column-width model (`src/views/TableLayout.ts:11-30`; `src/views/TableColumnLayoutSync.ts:4-79`), so the current placement is a presentation limitation rather than a data limitation.

10. **There is no value-to-filter bridge at the point of inspection.** The column menu provides hide, wrap, width, auto-fit, sort, and clear-sort actions (`src/views/ColumnMenu.ts:194-237`), while filter construction lives in a separate panel with type-specific operators (`src/views/FilterPanelRenderer.ts:74-98,192-370`). The database already has an append-and-refresh pattern for generated filter rules (`src/views/DatabaseView.ts:9829-9854`). A user examining a status, tag, or date value must currently remember the value and rebuild the condition elsewhere.

## Anytype/AppFlowy patterns

The comparison below uses the official product documentation and Anytype’s official explanation of Sets. It treats the products as pattern references, not as a request to copy their data models.

- [AppFlowy Grid View](https://appflowy-io-appflowy.mintlify.app/core/grid-view) makes the row-number gutter a compact control surface: row actions appear from the row number, the row number selects the whole row, and rows can be reordered there. This is more legible than a drag grip that appears only on row hover, because selection and row operations have a named, stable home.

- AppFlowy puts the field name, type icon, sort action, resize edge, and reorder affordance in the field header. Its grid docs also describe double-clicking a resize edge to auto-fit and using the header menu for an exact width. The plugin already has auto-fit and width actions, but putting them behind a reliably reachable header action—and supporting an explicit auto-fit gesture—would reduce the gap between capability and discoverability.

- AppFlowy documents typed cell behavior: text can be edited directly, select fields open their picker, dates open a picker, and checkboxes toggle with click or Space. This is a useful model for making the primary action reflect field type while retaining keyboard and range-selection escape hatches. It is better than making every cell look inert and reserving the only edit signal for a second click.

- AppFlowy’s grid grouping keeps the grid concept while adding collapsible groups and counts. Its calculations appear at the bottom of a column and update automatically. This anchors an aggregate to the field being measured, unlike a detached summary strip.

- AppFlowy exposes filtering from the toolbar with a condition builder and AND/OR choices, and exposes quick field sort plus a multi-sort menu. The pattern is a useful split: fast, local action for the common case; a structured panel for composing several rules.

- [Notion tables](https://www.notion.com/help/tables) use a row hover gutter for selection and drag actions, field-header menus for property visibility and wrapping, and per-column calculations such as count, unique values, and sums. [Notion view filters and sorts](https://www.notion.com/en-gb/help/views-filters-and-sorts) treats property visibility, filter, sort, group, and subgroup as settings of the current view. That stable per-view schema is the strongest reference for preventing a filtered result from changing which columns exist.

- Notion’s advanced filter groups and draggable multi-sort rules show the value of making rule composition visible rather than hiding it behind repeated header clicks. Its side-peek pattern is also relevant to a later row-detail iteration, but is intentionally left out of this table-focused recommendation set.

- [Anytype Sets](https://blog.anytype.io/a-new-metaphor/) frames a view as a collection of objects sharing relations, with sorting, filtering, and view choice applied to that collection. The relevant lesson is semantic stability: a view defines how known relations are presented; a transient filter should narrow the records, not redefine the relation/column inventory.

## Open threads for later iterations

- Test the stable-column decision against property creation, deleted frontmatter, and the existing auto-hide intent. A future iteration should define when a newly discovered field is considered part of a view versus merely available in the property manager.
- Decide whether a pinned identity column is worth the layout complexity. Notion’s freeze-column pattern is attractive for wide grids, but the current width-sync and grouped-table architecture should be simplified first; AppFlowy’s current documentation treats freeze columns as forthcoming.
- Specify a compact touch grammar for row selection, cell range selection, group selection, and opening row actions. The current phone move button and table-selection behavior should not compete for the same gutter pixels.
- Add focused QA fixtures for: a filter that removes all values from a column, a multi-sort with a narrow secondary column, a collapsed group with partial selection, ten groups sharing horizontal scroll, and a calculation footer after column reorder.
- Consider a later “view diagnostics” affordance for active sort/filter/group state, but keep this iteration centered on local grid affordances rather than repeating the broader empty-state and toolbar work from iteration 01.
