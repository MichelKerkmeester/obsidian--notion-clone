# Codex-Luna UI improvement research — iteration 03

## Focus

Popovers, menus, and dropdowns: elevation, structure, alignment, keyboard behavior, and hover interaction.

This iteration is deliberately about the interaction layer around a surface, not the table/grid affordances or empty-state semantics covered in iterations 01–02. The review treats every anchored surface as a small state machine: it has an invocation point, an alignment contract, a focus owner, a dismissal hierarchy, and a mobile/viewport policy.

The product constraints remain: recommendations must be mobile-safe, iCloud-safe and display-only (no note-body writes), MIT-forkable, and easy to rebase onto the upstream fork.

## Current-UI findings (file:line)

1. **Dismissal is opt-in, duplicated, and partly time-based.** `installPopoverAutoClose` defaults to a five-second inactivity close and does not close on outside pointer-down or Escape unless the caller opts in (`src/views/PopoverAutoClose.ts:11-12,37-79`). `DropdownField` adds its own outside listener and Escape handler (`src/views/DropdownField.ts:215-236`), while the database, title-actions, view-tab, group, and export popovers repeat the same outside-listener pattern (`src/views/ToolbarRenderer.ts:391-403,589-601,846-858,1197-1214,1688-1700`). This makes nested surfaces hard to reason about: a child can close itself while the parent remains visually open, or a parent can interpret a child click as outside unless every caller remembers another selector. Anytype’s menu lifecycle is a useful contrast because child menus bind their own key handling and restore the parent’s handling when they unbind.

2. **Anchoring is correct only at open time, and three important pickers bypass the shared geometry.** `positionToolbarPopover` measures, flips, clamps, and then retries once on the next animation frame (`src/views/PopoverPosition.ts:37-104`), but it does not observe visual-viewport changes, anchor movement, container scroll, or a soft keyboard after that. Column submenus use an independent fixed viewport clamp that always prefers the right side and hard-codes a 320px bottom allowance (`src/views/ColumnMenu.ts:565-593`); the color picker has a second below/above calculation based on `clientWidth/clientHeight` (`src/views/OptionColorPicker.ts:49-75`); cell option/relation popovers have a third placement algorithm (`src/views/CellRenderer.ts:2648-2695`). These surfaces can disagree about the safe bottom and can detach from a moving anchor.

3. **`DropdownField` has the visual shape of a listbox but not its keyboard model.** The panel is `role=listbox` and rows are `role=option` with `aria-selected` (`src/views/DropdownField.ts:141-168`), but there is no roving `tabindex`, `aria-activedescendant`, arrow/Home/End handling, typeahead, or selected-option scroll-into-view. Search focuses the input, then only hides rows and section headings (`src/views/DropdownField.ts:209-213,260-281`); it does not expose a no-results state or a “move from search into results” path. The only panel key handler closes on Escape (`src/views/DropdownField.ts:220-225`). This is especially costly in filter, sort, view-type, and settings panels because the same dropdown is reused everywhere.

4. **Column submenus are opened by three pointer events, with no equivalent intent model for keyboard users.** “Change type”, number style, and text render mode attach `mouseenter`, capture-phase `mousedown`, and capture-phase `click` to open a custom submenu (`src/views/ColumnMenu.ts:98-154`). The submenu itself has listbox semantics but no menuitem/submenu relationship (`src/views/ColumnMenu.ts:259-290`), and Escape simply removes the child (`src/views/ColumnMenu.ts:630-637`) without restoring the parent item’s focus. The 140ms hover grace (`src/views/ColumnMenu.ts:601-628`) is a good pointer bridge seed, but it should not be the only way to discover or reach the child.

5. **Body-hosted controls do not inherit the plugin’s focus treatment.** The plugin’s focus rules are scoped to `.note-database-container` (`styles.css:187-206`), while the color picker is appended to `doc.body` (`src/views/OptionColorPicker.ts:11-16`) and column submenus are also body-hosted (`src/views/ColumnMenu.ts:570-576`). The color swatches are `span` elements with `role=button` (`src/views/OptionColorPicker.ts:32-46`), and their selected state is only a CSS ring (`styles.css:5581-5608`). A body-hosted surface therefore has a different focus-visible result from a container-hosted dropdown, and a keyboard user can lose the focus location entirely after dismissal.

6. **The icon picker rebuilds its entire focus tree and silently caps the catalog.** Every tab/category/color change empties and recreates the panel (`src/views/IconPickerPopover.ts:57-69,89-99,151-160`); icon buttons expose titles but not selected state, tabs/categories are not tabs or a labelled tablist, and the catalog renders only `values.slice(0, 240)` (`src/views/IconPickerPopover.ts:118-147`). Arrow navigation assumes eight columns (`src/views/IconPickerPopover.ts:176-185`), which is not guaranteed by the responsive grid in `styles.css:15992-15999`. This is a subtle keyboard trap: after a re-render, the active element may be detached and the next arrow key starts from an arbitrary item.

7. **The mini-calendar communicates state visually, not structurally.** Day, month, and year cells are buttons with `title` attributes and selected/today classes, but the grids have no grid/row/column roles, `aria-selected`, `aria-current`, or roving focus (`src/views/CalendarMiniCalendarRenderer.ts:134-212`). Month navigation does preserve focus for the previous/next/title controls (`src/views/DateValuePicker.ts:250-260`), but choosing a month or year rebuilds the view without a focus target (`src/views/DateValuePicker.ts:294-309`). The existing IME guard is the right precedent for Enter/Escape handlers (`src/data/KeyboardUtils.ts:1-16`; `src/views/DateValuePicker.ts:207-214`), and should be retained while adding calendar navigation.

8. **The relation picker is a large, re-rendering multi-select hidden inside a single-option visual vocabulary.** It creates one button per record, filters by rebuilding the list, and toggles a CSS selected class/checkmark (`src/views/CellRenderer.ts:759-790`). The search input has no explicit listbox relationship or Down-to-results behavior, there is no no-results row, and each selection rebuilds the list without restoring the active option (`src/views/CellRenderer.ts:791-820`). The option picker’s keyboard handler supports only Up/Down/Enter plus Escape/Tab (`src/views/CellRenderer.ts:891-925`), while relation records can be much larger than the 260px option surface (`styles.css:5332-5347`). Anytype’s documented use of virtualized large lists points to a more scalable pattern here.

9. **Elevation and sizing express implementation history rather than a layer hierarchy.** Toolbar panels use `z-index: 50` and a faint shadow (`styles.css:8385-8408`), dropdowns use `80` or `1000`, color uses `1002`, chart menus use `70/90`, and the icon picker uses Obsidian’s `var(--layer-popover)` (`styles.css:1873-1889,3535-3926,5332-5347,5581-5593,15939-15952`). A late rule strengthens some shadows but excludes several body-hosted/custom cases because the selector is partly container-scoped (`styles.css:16429-16460`). Without named surface layers, adding one submenu or a mobile keyboard adjustment risks either blending into the table or covering the wrong sibling.

10. **Large settings surfaces have no local close affordance or explicit surface heading relationship.** The view settings panel renders a title only (`src/views/ViewConfigPanelRenderer.ts:253-255`) and relies on the toolbar toggle or outside behavior. Calendar and timeline options do the same (`src/views/CalendarToolbarRenderer.ts:65-75`; `src/views/CalendarTimelineToolbarRenderer.ts:47-52`). On a narrow viewport, where the panel may fill most of the available height (`styles.css:15287-15391,15721-15731`), requiring the user to find the original toolbar anchor to close is an avoidable focus and reachability problem.

## Anytype/AppFlowy patterns

### Anytype

- Anytype’s [menu-system notes](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/menu/README.md) describe one menu model that handles auto-flipping placement, animation, arrow/Enter/Escape navigation, mouse hover/click/active states, submenu management with a polygon connector, and an optional dimmer. The useful lesson is not the animation; it is ownership: a submenu knows it is a child, the parent remains a focusable state, and the pointer gets a forgiving path across the gap. That directly addresses the current `ColumnMenu`’s three-event hover opening and one-way right clamp.
- The same notes give menu items explicit affordance slots—icons, arrows, checkboxes, switches, descriptions—and mention virtualization for large lists. That creates a stronger information hierarchy than a list of indistinguishable text rows and supplies a ready pattern for current-value hints and large relation/icon catalogs.
- Anytype’s [Desktop 0.46 release notes](https://releases.any.org/desktop-0460) describe moving complex settings from a popup to a full-page layout and organizing property visibility/settings. The applicable pattern is an escalation rule: simple selection stays anchored; multi-section configuration gets a larger, clearly headed surface when the viewport is constrained.

### AppFlowy

- AppFlowy’s official [Grid View guide](https://appflowy-io-appflowy.mintlify.app/core/grid-view) describes a consistent interaction grammar: field-header menus expose actions from a single surface, select fields open a dropdown and close on outside click or Enter, date fields support arrow-key movement, and filters/sorts have explicit add-more flows. The benefit is predictability: the same commit and dismissal expectations apply whether the user is editing a cell or configuring a view.
- AppFlowy’s filter and sort documentation presents add-filter/add-sort as a staged sequence rather than a dense unlabelled row. That is a useful structure for the plugin’s nested filter/sort controls: the active step can own focus, while the parent surface remains available and the next choice is visibly scoped.

### Notion where useful

- Notion’s official [views, filters, sorts, and groups guide](https://www.notion.com/help/views-filters-and-sorts) groups view settings into Layout, property visibility, filter, sort, group, subgroup, and related actions, while exposing advanced filtering from the same menu. This is a strong information-architecture pattern for the plugin’s settings popover: section names should describe the decision being made, and current state should be visible without reopening another menu.
- Notion’s view menu also adapts page opening to screen size and offers side/center/full-page modes. The transferable principle is responsive escalation, not visual imitation: a tall multi-step picker should become a reach-friendly sheet or larger surface on phone, with a stable heading and footer actions.

## Open threads for later iterations

- Validate the overlay contract with keyboard, touch, mouse, IME composition, RTL, 200% zoom, narrow split panes, Obsidian mobile navbar, and a software keyboard that changes `visualViewport` height.
- Decide whether Obsidian’s `Menu` can be wrapped behind the same surface-stack contract or whether the custom menu renderer should become the single implementation; preserve MIT-compatible local behavior either way.
- Measure relation/icon catalog thresholds before choosing virtualization versus a searchable staged picker; retain deterministic focus indices when filtering or changing sections.
- Audit chart, calendar, timeline, board, and gallery-specific nested menus for the same parent/child focus and layer rules after the shared primitives land.
- Review localized labels, shortcut hints, and long translated section names for clipping before finalizing widths and mobile sheet breakpoints.
