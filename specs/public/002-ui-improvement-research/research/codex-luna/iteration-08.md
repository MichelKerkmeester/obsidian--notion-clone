# Iteration 8 — Beyond-table view parity

## Focus

This pass examines the board, gallery, calendar, and list as four projections of the same note set. The emphasis is parity of record activation, field budgets, grouping and movement feedback, creation affordances, and calendar-specific interaction—not another pass over the table, generic empty states, toolbar primitives, themes, or broad inspector patterns already covered in iterations 1–7.

The most important design principle is that a view may change the information hierarchy, but it should not make the same record feel like a different kind of object. All recommendations below are presentation/interaction-shell changes: they preserve the plugin’s existing data actions, add no note-body write path, and remain compatible with local vault storage and an MIT fork.

## Current-UI findings (file:line)

1. **Board, gallery, and list promise whole-item activation but implement only a small open button.** The three root surfaces all use `cursor: pointer` (`styles.css:7283-7290`, `styles.css:7804-7813`, `styles.css:8161-8175`), yet their renderers attach `openRow` only to the maximize button (`BoardRenderer.ts:598-607`, `GalleryRenderer.ts:197-205`, `ListRenderer.ts:176-185`). Titles are marked for Obsidian hover preview (`BoardRenderer.ts:617-621`, `GalleryRenderer.ts:217-221`, `ListRenderer.ts:198-202`), not for a complete click/keyboard activation contract. The result is a deceptive affordance: a user can tap empty card/row space that looks active but does nothing, while field values intentionally consume clicks for editing (`GalleryRenderer.ts:510-518`, `ListRenderer.ts:470-478`).

2. **Calendar events and non-calendar records open through different destinations with no visible view-level choice.** Calendar segments are real buttons and call `openRecordDetail` on click (`CalendarRenderer.ts:1398-1407`); `DatabaseView` wires that detail-panel callback for calendar (`DatabaseView.ts:386-399`). Board, gallery, and list are wired directly to `dataSource.openNote` (`DatabaseView.ts:614-674`). This is useful behavior in isolation, but it is an unexplained mode switch when a user changes views: the same row opens a detail panel in calendar and a note in the other views.

3. **Cover media has a second, competing activation model.** Board and gallery card surfaces are pointer-like, but their cover regions are explicit role-buttons that open the linked image/file target and stop propagation (`BoardRenderer.ts:659-696`, `GalleryRenderer.ts:442-474`). CSS reinforces `cursor: zoom-in` (`styles.css:7388-7396`, `styles.css:7887-7898`). There is an accessible image label, but not a distinct action label such as “Preview cover”; on a touch screen, a large cover is the most obvious place to tap and it does not open the record. Empty covers are not actionable at all (`BoardRenderer.ts:664-669`, `GalleryRenderer.ts:445-450`).

4. **Field value rendering has drifted between the three card/list surfaces.** Board and gallery mark multi-select, relation, and special file values as `has-badges` (`BoardRenderer.ts:1016-1037`, `GalleryRenderer.ts:543-565`), which exempts them from the normal two-line clamp; list does not add that marker for the same branches (`ListRenderer.ts:503-521`). The CSS then makes the difference visible: board and gallery badge containers wrap (`styles.css:7486-7492`, `styles.css:8026-8031`), while list badges stay one line, clip, and hide overflow (`styles.css:8312-8322`). Long tags, relations, or file links therefore communicate different amounts of the same property solely because the view changed.

5. **Title-field editing is list-only in practice.** List gives a custom title field an explicit click-to-edit handler (`ListRenderer.ts:209-225`). Board and gallery render the title and support double-click file-name rename, but have no matching custom-title edit branch (`BoardRenderer.ts:617-635`, `GalleryRenderer.ts:217-235`). Because all three titles also carry hover-link metadata, a single title gesture has an unstable meaning across views: preview/open in one place, inline edit in another, and rename only for file titles.

6. **Group-scoped creation is materially farther away in gallery/list than in board.** Board places `+ New` inside each group’s card stack and pre-fills the grouping field (`BoardRenderer.ts:361-374`; subgroup equivalent `BoardRenderer.ts:416-428`). Gallery and list place their group creation control after the visible items, expand control, and footer (`GalleryRenderer.ts:128-135`, `ListRenderer.ts:120-126`). On a long group, the action is below the fold; on a collapsed group it disappears with the body. The underlying defaulting behavior is already available, so this is an affordance-placement parity problem, not a new data-model problem.

7. **Sorted grouped movement has weaker feedback in gallery/list than in board.** Board gives every editable card `dragover` state, before/after placement, and a target highlight (`BoardRenderer.ts:524-540`), with corresponding CSS states (`styles.css:7303-7315`). Gallery and list fall back to a bare draggable card/row when the view is grouped and explicitly sorted (`GalleryRenderer.ts:333-347`, `ListRenderer.ts:327-340`); only the group header/container gets a generic `is-drop-target` outline (`GalleryRenderer.ts:409-427`, `ListRenderer.ts:403-421`, `styles.css:5102-5109`). Users cannot tell whether dropping on a group will append, change the grouping value, or preserve the sort, and the existing card-level drop styles are not consistently reached.

8. **Calendar creation still assumes mouse hover or mouse drag.** Month-day `+` is hidden until hover/focus (`styles.css:13202-13220`), while week/day all-day creation is wired to `dblclick` on the column (`CalendarRenderer.ts:524-537`). The date button’s single click intentionally does nothing and double-click navigates (`CalendarRenderer.ts:539-558`). Timed creation starts from `mousedown` and tracks `mousemove`/`mouseup` (`CalendarRenderer.ts:1229-1280`), with no pointer/touch path. This leaves a phone user without a reliably visible, one-tap create affordance and makes the day header’s gesture hard to discover.

9. **Calendar’s rendered projection has fewer diagnostics than the timeline projection.** The calendar month model returns only days/weeks (`CalendarTimelineModel.ts:488-543`); invalid events are filtered out of day cells (`CalendarTimelineModel.ts:518-533`). Events with no normalized start date are silently skipped (`CalendarTimelineModel.ts:764-780`), and an invalid/earlier end date is folded back to the start date before the event is emitted (`CalendarTimelineModel.ts:780-818`). The timeline model, by contrast, exposes `eventCount`, `visibleEventCount`, and `invalidEventCount` (`CalendarTimelineModel.ts:554-631`). Calendar has a separate invalid-warning button (`CalendarRenderer.ts:1491-1525`), but no common count/reason surface for undated, invalid, outside-window, and lane-overflow records across month, week, and day.

10. **Grouping state is not portable or self-explanatory across view switches.** Board resolves grouping from `boardGroupField` and can add a second subgroup (`DatabaseView.ts:2450-2478`, `DatabaseView.ts:9808-9814`); gallery and list resolve only `ViewStateStore`’s single `groupByField` (`DatabaseView.ts:9721-9751`). Switching from board to gallery/list therefore drops subgroup hierarchy and may use a different group field without an explicit explanation. This is not necessarily wrong—view-local settings are desirable—but the transition currently offers no “this view uses…” summary or indication of what was intentionally not carried over.

## Anytype/AppFlowy patterns

### Anytype

Anytype treats Grid/List/Gallery/Kanban/Calendar as first-class layouts over an object collection rather than unrelated screens. Its public documentation and client vocabulary keep those layouts alongside a common object model: [Anytype’s official docs repository](https://github.com/anyproto/docs) and [official desktop client](https://github.com/anyproto/anytype-ts). The useful pattern here is object continuity: the same icon/title/identity and open behavior remain recognizable while the layout changes. Anytype’s local-first positioning is also a good fit for this fork: layout polish should be cacheable UI state, not a reason to rewrite note bodies.

Adoptable lessons:

- Make the record hit area and the property-specific hit areas distinct. “Open object” should be predictable; media preview, checkbox, property edit, and move should be visibly secondary actions.
- Treat layout settings as view-local and disclose them. A board’s grouping hierarchy need not silently become a gallery’s grouping hierarchy, but the user should see the active view’s grouping and property budget.
- Preserve object identity cues in compact views. A record icon/title anchor and a stable secondary open action help list, board, and gallery feel like different lenses on one object.

### AppFlowy

AppFlowy’s architecture documentation explicitly says Grid, Board, and Calendar share database structs and that field type/options control formatting: [Database View](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/frontend/database-view). Its board docs define a group as a state, a card as a database row, and movement between groups as an update to the grouping cell; they also describe both top-right and bottom group creation affordances and keyboard actions such as Enter to open and N to create: [Kanban Board](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/frontend/database-view/kanban-board). Its calendar documentation calls out a dedicated “other events” treatment for records whose date is empty: [Calendar](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/frontend/database-view/calendar).

Adoptable lessons:

- Share a typed field-display contract across views. The same property type should get the same badge/link/date semantics, with a view-specific budget rather than view-specific meaning.
- Put creation where the group context is visible, and make that context part of the action preview. A `+ New` inside a group is easier to trust than a global button followed by a hidden default.
- Treat movement as a state-changing operation that needs a target preview and a clear grouping consequence. This is especially important when sort order means position is not user-controlled.
- Keep a visible “not placed here” route in calendar. A record missing its date should be discoverable as an intentional other/unscheduled set, not silently absent.

### Notion (useful comparison)

Notion’s current help documentation is a strong reference for view-local semantics: [Views, filters, sorts & groups](https://www.notion.com/help/views-filters-and-sorts) describes per-view layout, property visibility, filter, sort, group, and subgroup settings. It also exposes a per-view “Open pages in” choice—side peek, center peek, or full page—and documents different defaults for Board/List versus Gallery/Calendar. Its overview differentiates Gallery as image-forward and List as minimal while keeping the same database pages underneath.

The important pattern is not visual imitation; it is an explicit contract. A view should state what it shows, how a record opens, how grouping works, and what is hidden or collapsed. That contract makes parity measurable and prevents a mode switch from feeling like data loss.

## Open threads for later iterations

- Validate the proposed hit regions with keyboard focus, screen readers, right-to-left layouts, touch targets, and Obsidian Page Preview hover behavior; especially verify that field editing and media links remain reachable without event bubbling regressions.
- Test the shared field budget against very long relations, many tags, broken image links, narrow embeds, and dynamic card resizing; decide whether `+N` should open a popover or a detail panel per view.
- Measure calendar month/week/day projection counts against the timeline model with missing dates, malformed dates, cross-midnight ranges, and dense overlapping lanes; keep the user-visible reason vocabulary stable across locales.
- Decide whether view-local open destinations should be persisted per saved view or remain a workspace/session preference; this is a product decision, not a renderer detail.
- Revisit timeline/chart parity after these four record-oriented views have a shared activation and projection contract.
