# Iteration 10 — Mobile / responsive / accessibility

## Focus

This pass examines the fork’s mobile and accessibility behavior at the seams between CSS, DOM semantics, pointer input, keyboard ownership, Obsidian’s mobile chrome, and assistive technology. Earlier iterations already covered the broad toolbar, popover, view-parity, selection, and generic focus/target-size themes; the new angles here are interaction-mode drift, gesture arbitration, embedded-view parity, accessible two-dimensional tables, and viewport/safe-area disclosure.

The constraint is a display-layer improvement only: recommendations may change view configuration UI or in-memory interaction state, but must not write note bodies. All recommendations are intended to remain local to the MIT fork and easy to rebase.

## Current-UI findings (file:line)

- **CSS and JavaScript have different definitions of “mobile.”** The responsive CSS switches at `max-width: 760px` for any narrow container (`styles.css:15287-15337`), while phone-only behavior is keyed to the global `body.is-phone` class (`styles.css:15340-15406`). The full view and embedded renderer independently ask that global body class in `src/views/DatabaseView.ts:4340-4342` and `src/views/EmbeddedDatabaseRenderer.ts:3526-3528`; `TableRenderer` uses that answer while rendering phone move controls (`src/views/TableRenderer.ts:513-524`). A narrow desktop split pane can therefore receive the stacked CSS without the phone interaction grammar, while rotation or a changed Obsidian pane can leave already-rendered listeners/controls stale.

- **The fixed mobile surfaces are not using one viewport/safe-area model.** Ordinary mobile panels use `100vh` (`styles.css:15324-15337` and `styles.css:15721-15731`), the view reserves a hard-coded `80px` for the Obsidian bottom bar (`styles.css:15351-15354`), and the body-mounted column-width sheet uses a plugin custom property rather than the native safe-area environment (`styles.css:15638-15660`). `PopoverPosition` does measure `visualViewport` and the mobile navbar (`src/views/PopoverPosition.ts:124-147`), but the sheet is created independently on `document.body` (`src/views/DatabaseView.ts:10272-10282`) and is not fed those bounds. A keyboard, landscape home indicator, or unusual bottom navigation height can therefore occlude controls or leave excessive dead space.

- **Several actions are visually compact enough to be hard to tap or discover.** Mobile move buttons are only `24px`/`26px` (`styles.css:15560-15594` and `styles.css:15606-15620`), board/gallery open buttons are `24px` (`styles.css:7334-7347` and `styles.css:7925-7938`), group expansion actions have no explicit hit box and are padded to zero (`styles.css:8234-8250`), and timeline jump buttons are `18px` and can become `pointer-events:none` over an event (`styles.css:15077-15125`). Calendar “more” events are plain clickable text rather than a button (`styles.css:13236-13246`). The existing visible focus outline is useful, but it cannot make a hidden or tiny target reliably operable.

- **Touch scrolling and selection/dragging compete at the event layer.** Full-view cell selection calls `preventDefault()` from a `mousedown` handler and changes to a tap-to-extend model on phone (`src/views/DatabaseView.ts:4294-4327`); embeds use the same mouse-only `mousedown`/`mouseenter` design (`src/views/EmbeddedDatabaseRenderer.ts:3487-3524`). Calendar time-range creation and event movement also start from mouse events (`src/views/CalendarRenderer.ts:1229-1280`), as does timeline movement/resizing (`src/views/CalendarTimelineRenderer.ts:1196-1275`). The timeline explicitly allows only vertical touch pan (`styles.css:14263-14268`). This is fragile for touch, pen, trackpad emulation, and long-press: a scroll can be claimed as a drag, while a range drag cannot be expressed consistently on mobile.

- **The full table has a real keyboard grid, but an embed does not.** Full view handles Tab, arrows, Home/End, PageUp/PageDown, Enter, and F2 (`src/views/DatabaseView.ts:1510-1567`) using shared resolution logic (`src/data/TableKeyboardNavigation.ts:29-82`). The embedded view registers a container keydown listener (`src/views/EmbeddedDatabaseRenderer.ts:421-434`), but its handler only implements copy and Escape (`src/views/EmbeddedDatabaseRenderer.ts:3425-3439`). An embedded database inside a note is therefore materially less usable with an external keyboard or switch/speech navigation than the same database opened as a view.

- **Table semantics stop at native tags, and some controls are deliberately removed from the tab sequence.** `TableRenderer` creates tables and headers but does not supply a table name/caption, header associations, row/cell indices, or selection state (`src/views/TableRenderer.ts:69-85` and `src/views/TableRenderer.ts:422-454`). Row checkboxes have no accessible name (`src/views/TableRenderer.ts:501-530`), and the editable record-icon button is explicitly forced to `tabindex=-1` to protect the spreadsheet roving tab stop (`src/views/TableRenderer.ts:531-537`). The trade-off avoids extra Tab stops but makes the icon action unreachable by ordinary keyboard focus, especially in table layouts.

- **Document-level shortcut capture uses pointer hover as a fallback for focus.** `DatabaseView` installs document-wide key handlers (`src/views/DatabaseView.ts:1206-1229`), then accepts database shortcuts when the container merely matches `:hover` even if `activeElement` is elsewhere (`src/views/DatabaseView.ts:1430-1440`). Several interactive surfaces are mounted outside that container, including the mobile column sheet (`src/views/DatabaseView.ts:10272-10360`) and icon/color pickers (`src/views/IconPickerPopover.ts:23-27` and `src/views/OptionColorPicker.ts:15-28`). On a desktop with an external keyboard, or when an Obsidian editor is hovered behind a popover, the fallback can steal keys from the user’s actual focus context; the container query also cannot reliably describe a body portal’s ownership.

- **Focus styling and motion reduction are scoped too narrowly for the portal architecture.** Focus is reset and restyled only under `.note-database-container` (`styles.css:189-206`), and reduced-motion rules also only cover descendants of that class (`styles.css:208-217`). Body-mounted pickers and the mobile width sheet are therefore outside both contracts. The width sheet listens for Escape and removes itself but does not establish a dialog role, initial focus, focus return, or modal label (`src/views/DatabaseView.ts:10333-10360`). This creates a keyboard/screen-reader escape path that is not visible in the static layout.

- **The timeline’s viewport optimization is semantically opaque.** The model intentionally creates a viewport-sized window from the current width (`src/data/CalendarTimelineModel.ts:336-365`), keeps all events in the model, and represents out-of-window events as jump indicators (`src/data/CalendarTimelineModel.ts:554-631`). The renderer preserves the window across resize (`src/views/CalendarTimelineRenderer.ts:217-255` and `src/views/CalendarTimelineRenderer.ts:1924-1948`), but the UI hides horizontal overflow and suppresses horizontal touch pan (`styles.css:14263-14268`). A sighted mouse user can infer the 18px jump affordances; a screen-reader or touch-only user gets no durable announcement of the visible date range, hidden-event count, or equivalent previous/next navigation.

## Anytype/AppFlowy patterns

- **Anytype: context-sensitive surfaces and a focus service.** Anytype’s public component documentation separates left navigation, right contextual detail, and progress surfaces instead of treating them as incidental overlays ([sidebar component README](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/sidebar/README.md#readmemd)). Its drag documentation also describes integration with a selection provider and a `focus` service ([drag component README](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/drag/README.md#readmemd)). The useful pattern for this fork is ownership: the active database, embedded database, picker, and inspector should declare which surface owns keyboard/pointer input. That is more robust than using `:hover` as a proxy for focus and scales to body portals.

- **Anytype: logical list state survives virtualization.** Anytype documents virtual scrolling, pagination/infinite scroll, and range-selection APIs in its list components ([list component README](https://github.com/anyproto/anytype-ts/blob/develop/docs/src/ts/component/list/README.md#readmemd)). The transferable idea is to keep focus and selection keyed to stable record/column identity while DOM rows are recycled or replaced. It is particularly relevant to the timeline window and grouped tables: announce the logical range/count, then move focus to the nearest surviving identity after a resize or viewport jump.

- **AppFlowy: an explicit grid interaction contract.** AppFlowy’s grid documentation names row numbers, row selection, row reorder, field headers, direct editing, and the keyboard grammar (Tab/Shift+Tab, arrows, Enter, F2, Escape, and create-row) ([Grid View](https://appflowy-io-appflowy.mintlify.app/core/grid-view)). This is a better accessibility model than treating a grid as a collection of clickable cells: the row/column relationship is explained, the focus model is predictable, and detail view is the escape hatch for complex fields. The fork should apply the same contract to embeds and expose the row/column context to assistive technology.

- **Notion: mobile removes hover and deliberately simplifies layout.** Notion’s mobile guidance says hover-only controls become persistent `•••`/`+` actions and desktop columns collapse to one column ([Notion for mobile](https://www.notion.com/help/notion-for-mobile)). Its workspace guidance also keeps a bottom navigation bar present and places an editing toolbar above the keyboard ([Workspaces on mobile](https://www.notion.com/help/workspaces-on-mobile)). The pattern worth adopting is explicit mobile disclosure: preserve the visual density of cards/tables where useful, but promote actions into a predictable row menu and move editing controls away from the keyboard’s occlusion zone. For the plugin’s inherently two-dimensional table, this argues for a labeled record/detail presentation as the reflow alternative rather than pretending horizontal scroll is a complete accessibility solution.

- **Accessibility baseline: target size, reflow, and unobscured focus.** WCAG 2.2’s minimum target-size criterion allows a `24px` target only with specific spacing/equivalent-function exceptions ([Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)); Apple’s platform guidance recommends a `44pt` button hit region and respecting safe areas ([Apple buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) and [Apple layout](https://developer.apple.com/design/human-interface-guidelines/layout)); WCAG reflow explicitly recognizes data grids as two-dimensional exceptions but still expects non-grid content to reflow ([Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). WCAG also calls out focus that is hidden by sticky/fixed content ([Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)). These are useful acceptance tests for the Obsidian mobile navbar, sticky table header, timeline jump controls, and fixed sheets—not just visual polish.

## Open threads for later iterations

- Test the mode switch matrix on Obsidian iOS/Android, rotation, split panes, tablet widths, hardware keyboard, VoiceOver, TalkBack, Dynamic Type/large text, and forced-colors emulation.
- Decide whether the table’s mobile fallback should be a record-detail disclosure, a row-card projection, or a user-invoked “reflow” mode; keep the two-dimensional grid available where it is semantically necessary.
- Measure the actual Obsidian mobile navbar and keyboard visual viewport rather than baking assumptions into CSS; verify that the plugin custom safe-area variable is populated on every supported host.
- Define the shared interaction-scope and pointer-gesture primitives before changing individual renderers, so calendar, timeline, table, and embedded views do not evolve four slightly different contracts.
- Audit localized accessible names and announcements, especially date ranges, group labels, row paths, icon names, and “N more” content, with a screen reader rather than relying on tooltips.
