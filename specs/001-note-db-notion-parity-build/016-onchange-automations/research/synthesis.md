# Synthesis: On-change Automations / Triggers
> One-line: ranked Notion-parity enrichment for this feature, synthesized by Grok 4.6 (xhigh-fast) from the phase's 10 research iterations. Evidence trail: research.md.

## Verdict
Do **not** build this. Wave 6 already recorded on-change automations, triggers, cron templates, and network buttons as out of scope on an iCloud-synced personal-finance vault (`spec.md` REQ-001/REQ-002; parent map: Wave 6 is never-default). The 10 iterations prove a EuroFormat-shaped engine is **design-ready** if the spec’s single revisit trigger fires (non-iCloud backend **or** a safe first-class Obsidian change-hook), because the fork already has origin-tagged `onDataChanged` batches, FilterRule matching, and serialized writes — but they do **not** overturn the hold. The single biggest risk is that iCloud/Obsidian Sync pulls still look like user edits: `vault.on("modify")` has no official origin bit, so a second desktop treating `origin === "external"` as “when field X changed” will write, sync, and retrigger ([obsidian-log-keeper#23](https://github.com/jimjambimbam/obsidian-log-keeper/issues/23); `DataSource.ts:163-166` only classifies **this process’s** owned credits, not foreign sync).

## Recommended build (locked design)
**Ship lock (now):** no new module, no call-site edit, no CSS. `plan.md` is explicit: “There is no implementation sequence, no new module under `src/data/`, and no call-site edit.” Algorithm below is frozen for the revisit trigger only.

**Core algorithm (post-revisit only):** a 5-stage evaluator that never registers `vault.on` itself.

1. **Subscribe** — `dataSource.onDataChanged` only (`DataSource.ts:124-129`), same pattern as `DatabaseView.ts:742` and `EmbeddedDatabaseRenderer.ts:422`. Drop `origin === "plugin"` batches. Raw `vault.on("modify")` is ruled out: DataSource already wraps it (`DataSource.ts:145-192`) and a second listener bypasses owned-path credits (`DataSource.ts:2009-2055`; Syncline’s per-kind cookies: [syncline#102](https://github.com/tomas789/syncline/pull/102)).
2. **Diff** — change unit = `(path, field, oldValue, newValue)`. Old value from the engine’s snapshot (`getRecordSnapshot`, `DataSource.ts:239-244`); new value from the batch path; compare with the same semantics as `valuesEqual` (`DataSource.ts:1730-1736`). This is AppFlowy’s `update_cell` → capture `old_row` → `did_update_row(old, new, field_id)` (`database_editor.rs:995-1076`). Carry values in the diff (do not copy AppFlowy’s field-id-only `UpdatedRowPB`); Notion webhooks are signal-only and force a follow-up GET ([Notion webhooks](https://developers.notion.com/reference/webhooks)) — the vault can avoid that tax.
3. **Match** — `QueryEngine.applyFilters(..., "and"|"or")` (`QueryEngine.ts:74-95`) over `FilterRule[]` (`types.ts:137-141`) plus a transition chip (changed to / from / any). Optional formula predicates: `evaluateBaseFilterExpression` (`BaseExpression.ts:59-62`). No new expression language.
4. **Act** — sequential local actions only: `editProperty` (set/add/remove/clear), then `addRecord` if in scope. Every write through `enqueueWrite` (`DataSource.ts:99-122`) so `markOwnedPath` mints 5s metadata+vault credits before IO; `frontmatterOverrides` keep the UI consistent for 10s (`DataSource.ts:1664-1688`). Hard no-chaining: actions are plugin-origin, so stage 1 never re-enters ([Notion: automations cannot trigger automations](https://www.notion.com/help/category/automations)).
5. **Record** — in-memory run log shaped like Anytype’s `{ id, type, status, createTime, isLocal, payload }` (`anytype-ts/.../model/notification.ts:6-21`); optional bounded ring buffer in plugin settings JSON, **never** vault frontmatter (`store/notification.ts:49-57` is UI state, not an object write).

**Debounce stack (all three, not one):** DataSource 80ms merge (`DataSource.ts:1994-1998`) → RefreshCoordinator idle 2s / max 10s (`RefreshCoordinator.ts:97-103`, `RefreshCoordinator.ts:61`) → engine trailing 3s per `(ruleId, path)` with cancel-on-newer (AppFlowy `DebounceNotificationSender`, `debounce.rs:28-52`; Notion’s 3s window). Failure: retry at most twice per change (RefreshCoordinator re-queue on error, `RefreshCoordinator.ts:140-144`); pause the engine after five consecutive failures (spec risk: write storms).

**EuroFormat integration (post-revisit only; 1 module + 3 call sites):**
- **Module:** `src/data/AutomationEngine.ts` — types, snapshot cache, subscribe/diff/match/act/log, `start()` / `destroy()`. Header discipline matches `EuroFormat.ts:8-9` (“Kept in one module so it stays a small, rebasable diff.”). Do **not** add `AutomationTypes.ts` / `AutomationModal.ts` / `AutomationListRenderer.ts` in the first slice; those extra files are research gold-plating past the 1-module pattern.
- **Call site 1 — `src/main.ts` ~212–213:** after `this.dataSource = new DataSource(this.app); this.dataSource.startListening(...)`, construct and `start()` the engine; `onunload` calls `destroy()` (mirror `DataSource.destroy`, `DataSource.ts:195-210`). On `Platform.isMobile`, skip `start()` of evaluation (list may still render).
- **Call site 2 — `src/settings.ts` `DEFAULT_SETTINGS` 21–33:** add `automations: []` (and the matching `PluginSettings` field / `createDefaultSettings`).
- **Call site 3 — `src/settings.ts` `SettingsTab.display()` ~61+:** one settings group: rule rows, enabled toggle, last-run chip, Add/Edit inline using existing filter widgets. No ribbon, no command view, no toasts per run.

Imports are one-directional: the engine imports `DataSource` / `QueryEngine` / `BaseExpression` / `types`; only `main.ts` and `settings.ts` import the engine. That is the EuroFormat graph (`EuroFormat.ts` imported only from `CellRenderer.ts:13` and `SummaryRenderer.ts:7`).

## Edge cases & mobile/iCloud safety
**Why the current phase is safe:** it writes nothing. Display-only in the parent sense: no hook, no template runner, no network send (`plan.md` affected-surfaces table; parent NFR: no churny writes on iCloud). DataSource owned-path windows stay the only echo defense (`DataSource.ts:2009-2055`) and this phase must not wrap, replace, or bypass them.

**If the frozen engine is ever applied, these cases are mandatory:**

- **Sync-as-external (the residual loop):** owned-path credits suppress *this* process’s writes, not Device B’s iCloud pull. `workspace.on("editor-change")` is user-only but open-file-only ([log-keeper#23](https://github.com/jimjambimbam/obsidian-log-keeper/issues/23)). Two desktops both running the engine remain unsafe; the spec’s non-iCloud (or first-class hook) trigger is the real gate, not “we subscribed to `onDataChanged`”.
- **iCloud uploader mtime churn:** iCloud can rewrite files during upload; ecosystem mitigation is debounce past the notify window ([obsidian-icloud-mirror](https://github.com/AngelCLA/obsidian-icloud-mirror); [mnott/Obsidian-iCloud](https://github.com/mnott/Obsidian-iCloud) three-way mtime). Engine window ≥ 3s; never add a parallel mtime writer.
- **Closed-app / mobile / CLI edits:** reconcile on `start()` against `getRecordSnapshot` (`DataSource.ts:239-244`); iCloud can present delete+create with a fresh mtime ([Vault Change Feed](https://community.obsidian.md/plugins/vault-change-feed)) — treat identical-content delete+create as rename (`DataSource.ts:175-191` already remaps overrides).
- **Field lifecycle:** rules key by property key (`FilterRule.field`). `ColumnPropertySync.rename/delete/convert` (`ColumnPropertySync.ts:22-53`) can orphan a rule — validate at load/eval, surface “field X no longer exists”, re-check operators with `getFilterOperatorsForColumn` (`FilterPanelRenderer.ts:19-40`). Never fail silent.
- **Missing/renamed database:** `databaseId` miss → skip and disable-with-reason; remap `oldPath→newPath` from DataSource rename (`DataSource.ts:175-191`).
- **Rule interactions:** no chaining (plugin origin). Two rules on one field: last-writer-wins by stable id order, documented in the UI.
- **Permission / scope:** actions write only inside the target database’s source rules; coerce values via existing column types (no raw YAML injection; `BaseExpression` already blocks `fetch`/`eval`).
- **Performance:** lazy per-changed-path snapshot, O(fields in that file) diff, O(rules × matched files) match; ring-buffer the log. A personal-finance vault (hundreds of files, dozens of rules) stays cheap if you never full-vault re-diff.
- **Failure storms:** max two retries per change; pause after five consecutive failures (`RefreshCoordinator.ts:113-144` as the retry idiom).
- **Mobile:** evaluation + actions off (`Platform.isMobile`). Settings list may be readable; Add/Edit/Delete disabled. Parent doctrine is display-only unless the spec says otherwise — this spec says otherwise only after revisit, and even then mobile stays display-only. Desktop remains the only writer; that invariant fails if two desktops are online (see open questions).
- **Run log persistence:** if a ring buffer is stored in plugin `data.json`, that file can sync via iCloud/Obsidian Sync. Keep it small and never write run history into note frontmatter.

## Open questions / operator decisions
Spec §7 records **no** further decision to *stay* out of scope. These are the only calls that change a later build, each with a default:

1. **When does the revisit trigger actually fire?** Spec: non-iCloud storage **or** a safe first-class Obsidian change-hook (`spec.md` REQ-003). **Default:** honor the OR, but treat “safe hook” as an API that distinguishes user edits from sync/iCloud metadata echo — `onDataChanged` + owned-path credits are **not** that hook ([log-keeper#23](https://github.com/jimjambimbam/obsidian-log-keeper/issues/23)). Do not reopen on design-readiness alone.

2. **Is a single-desktop writer enough?** Research assumed one desktop engine + mobile display-only. **Default:** not enough. Stay out of scope until storage is non-iCloud **or** the hook can ignore sync pulls on every machine that would run the engine.

3. **Use `editor-change` as an extra origin hint?** **Default:** no for v1. It misses closed-file and other-app edits and would split the trigger definition. Reconsider only as a *narrowing* filter on top of DataSource, never as the sole source.

4. **Include bulk “Edit pages in” in the first post-revisit slice?** **Default:** no. Finance-vault blast radius; ship same-row `Edit property` (+ optional `addRecord`) first. Require affects-N if it ever ships.

5. **Where do rules live — plugin settings vs per-database view config?** **Default:** `automations[]` in plugin settings with optional `databaseId` (one-line `DEFAULT_SETTINGS` edit; EuroFormat-sized). View-level storage can wait.

6. **Persist the run log in `data.json`?** **Default:** memory-first, last ~200 runs in settings only if operators need history across restarts; never in note YAML. Accept that `data.json` may sync; do not treat that as vault note churn.

7. **Network / cron later, behind a flag?** **Default:** no. REQ-002 and Notion’s own webhook limits do not create a people/identity model. Cron is not a Notion automation trigger ([Thomas Frank](https://thomasjfrank.com/notion-database-automations-the-complete-guide/)).
